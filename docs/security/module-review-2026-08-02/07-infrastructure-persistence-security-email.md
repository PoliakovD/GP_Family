# Модуль: Инфраструктура — крипто, EF-модель, хранилище файлов, email, аудит

**Файлы:** `Infrastructure/Security/*`, `Infrastructure/Persistence/*` (включая
`Configurations/*`), `Infrastructure/Storage/*`, `Infrastructure/Email/*`, `Infrastructure/Audit/*`

**Статус:** 🟡 2/2 закрыты (находка 1 — код изменён; находка 2 — проверено, поведение уже
соответствует ожидаемому). 🟢 находка 3 — подтверждена как ожидаемая, действий не требовалось.

## Сводка

Криптография (AES-256-GCM для полей и файлов, PBKDF2 для паролей, SHA-256+HMAC для токенов) сделана
корректно и последовательно, с понятным форматом версионирования ключа (`enc:{keyId}:{payload}`) —
задел под ротацию уже есть, хотя сама процедура ротации (перешифровка) нигде не реализована (это,
похоже, осознанно вне текущего скоупа). EF-конфигурации согласованы с ручной чисткой FK-less связей,
описанной в комментариях сервисного слоя (перепроверено — комментарии не расходятся с кодом).
Находки — по краям: параллельное развёртывание, устаревание `AllowLegacyPlaintextRead`.

## 🟡 Средний приоритет

### 1. `EncryptionOptions.AllowLegacyPlaintextRead = true` по умолчанию — тихо принимает незашифрованные значения

> ✅ **Исправлено — убрано целиком, а не смягчено логом/алертингом.** Проект ещё в активной
> разработке: реальных БД с "переходным периодом миграции" не существует, локальные окружения
> пересоздаются с нуля, поэтому сам сценарий "легаси-строка без enc:-префикса" неактуален. Флаг
> `AllowLegacyPlaintextRead` и весь легаси-путь чтения удалены из `EncryptionOptions` и
> `AesGcmFieldCipher.Unprotect` — чтение значения без префикса `enc:` теперь безусловно бросает
> `InvalidOperationException`, как и должно быть для системы, где шифрование обязательно с самого
> начала. Тесты обновлены (`AesGcmFieldCipherTests.Unprotect_PlaintextValue_AlwaysThrows`).

- **Где:** `Infrastructure/Security/EncryptionOptions.cs:14-18`,
  `AesGcmFieldCipher.Unprotect:69-77`.
- **Проблема:** если `AllowLegacyPlaintextRead` включён (дефолт `true`), чтение значения без
  префикса `enc:` тихо возвращает его как есть — без предупреждения/лога о том, что конкретная
  строка не зашифрована. Задумано для переходного периода миграции на шифрование, но нет активного
  контроля/алертинга, который просигнализировал бы, когда переходный период фактически закончился и
  флаг пора выключить (комментарий в коде говорит «выключить после полной перешифровки данных», но
  не описывает, как узнать этот момент).
- **Рекомендация:** либо добавить метрику/лог-warning при каждом legacy-чтении (чтобы было видно,
  когда их количество упадёт до нуля), либо явную одноразовую джобу-проверку/скрипт, подтверждающий
  отсутствие legacy-строк перед выключением флага в проде.

### 2. Счётчики суточного лимита SMTP-провайдера — в памяти процесса, не переживают рестарт/масштабирование

> ✅ **Подтверждено как приемлемое поведение — проверено, изменений в коде не потребовалось.**
> Перечитан `MailKitSmtpEmailSender.SendAsync`: превышение суточного лимита УЖЕ приводит только к
> `logger.LogWarning(...)` и переключению на следующего провайдера (или итоговое исключение, если
> провайдеров/лимитов не осталось совсем) — счётчик никогда не блокирует процесс и не роняет
> запрос молча. То, что счётчик живёт в памяти процесса (не переживает рестарт/масштабирование) —
> осознанно принято как есть: при превышении реального дневного лимита провайдера SMTP просто
> ответит ошибкой, что уже обрабатывается тем же `catch` (провайдер помечается недоступным до
> конца попытки, лог о сбое есть). Не требует ни персистентного счётчика, ни иного поведения.

## 🟢 Низкий приоритет / на заметку

### 3. Нет процедуры ротации ключа шифрования (`ActiveKeyId`) — только формат, готовый её принять

> ✅ **Подтверждено как ожидаемое для текущей стадии — действий не требовалось.** Формат уже
> версионирует ключ (`enc:{keyId}:{payload}`), сама процедура перешифровки сознательно не
> реализуется сейчас — задел на будущее, фиксируется здесь только чтобы не забыть при первой
> реальной ротации. Изменений в коде нет.
>
> **Обновление 2026-08-25:** реализовано в ADR-0009 (`IEncryptionKeyRing`, `EncryptionRotationJob`,
> вкладка «Ключи» админ-панели) — см. этот ADR для процедуры.

- **Где:** `Infrastructure/Security/AesGcmFieldCipher.cs:82-84`, `AesGcmFileCipher.cs:68-70` —
  обе реализации при несовпадении `keyId` бросают исключение с текстом «требуется ротационная
  перешифровка», но самого механизма/джобы перешифровки в кодовой базе не найдено. Ожидаемо для
  текущей стадии проекта (задел на будущее), не баг — фиксируется, чтобы не забыть при первой
  реальной ротации ключа.

### 4. `TokenHasher`/OTP-хеши — обычный SHA-256 без соли, но для случайных высокоэнтропийных секретов это корректно

- **Где:** `Infrastructure/Security/TokenHasher.cs`.
- Используется для refresh-токенов (32 случайных байта), кодов привязки Telegram (16 случайных
  байт), email-кодов (6-значные числа — НО с отдельным rate-limit/lockout по попыткам, не голым
  хешем). Для refresh-токенов/link-кодов простой SHA-256 без соли — стандартная и корректная
  практика (энтропия самого секрета делает радужные таблицы бессмысленными). Для 6-значных
  email-кодов соль тоже не нужна, т.к. защита строится на TTL+лимите попыток, а не на стойкости
  хеша к перебору всех 10^6 вариантов оффлайн (сам хеш никогда не «утекает» отдельно от остальной
  БД, а если утекла вся БД — сессия/аккаунт скомпрометированы куда более прямыми путями). Не
  находка, зафиксировано как проверенное и корректное решение.

## ✅ Проверено, проблем не найдено

- `AesGcmFieldCipher`/`AesGcmFileCipher` — случайный 12-байтовый nonce на каждое значение/файл,
  16-байтовый тег аутентичности, ключ обязателен (fail-fast в `Program.cs`, если
  `Encryption:MasterKey` пуст), декодирование ключа проверяет длину (32 байта/AES-256).
- `PasswordHasher` — см. также [01-auth-identity.md] — PBKDF2 210k итераций, constant-time verify.
- `DownloadTokenService` — HMAC-SHA256 подпись `{attachmentId}:{expiresAtUnix}`, constant-time
  сравнение, явная проверка истечения до сравнения подписи.
- EF-конфигурации (`Infrastructure/Persistence/Configurations/*`) — уникальные индексы и
  каскадные/restrict-политики соответствуют комментариям в сервисном слое (`FamilyMedicalShare`/
  `MedicalRecordHidden` действительно без FK на `Family`, что явно ожидается и обрабатывается
  вручную в `FamilyService.DeleteFamilyAsync`/`AccountService.DeleteAccountAsync`/
  `UserLeftFamilyMedicalCleanupHandler`).
- `kb`-схема физически отделена от `identity`/`medical` схем в самой БД (`ToTable(...,"kb")`) —
  дополнительный (не только логический) барьер изоляции обезличенного справочника.
- `LocalFileStorage`/`MinioFileStorage` — оба хранят только шифротекст (шифрование происходит на
  уровне `AttachmentService` до вызова `IFileStorage.SaveAsync`), явных прямых/presigned ссылок на
  сырые блобы не найдено — всё скачивание идёт через собственный API-эндпоинт с расшифровкой.
- `MedicalAuditWriter`/`AuditRetentionJob` — синхронная запись аудита в момент авторизации, retention
  12 месяцев, ежемесячная чистка через Hangfire recurring job.
- Раздельные email-шаблоны (`EmailTemplateRenderer`) — все подстановки в HTML-письма проходят
  `WebUtility.HtmlEncode` до вставки в шаблон (включая код/email/пароль), кроме уже отрендеренного
  `ContentBlock` (второй проход, который по построению не должен повторно экранироваться) —
  корректная защита от HTML-инъекции в письма через код/пароль/email пользователя.
