# Модуль: Angular-фронтенд (FamilyHub.Web)

**Файлы:** `FamilyHub.Web/src/index.html`, `app/services/auth.*.ts`, `app/services/telegram.service.ts`,
`app/services/api.service.ts`, компоненты `consent-gate`, `consent-text`, `login`, `privacy`,
`dev-panel`, `settings/security/*`

**Статус:** 🟡 2/2 закрыты, 🟢 3/3 закрыты (находки 3, 4, 5 — код изменён либо подтверждено, что
изменений не требовалось).

## Сводка

Клиентская логика аутентификации/интерцептора сделана вдумчиво (дедупликация in-flight запросов,
разделение session-less путей от обычных для избежания циклов refresh, явный запрет кэширования
API-ответов после реального инцидента с WebView). Единственный `bypassSecurityTrustHtml`-паттерн
используется только для статического, серверно-контролируемого юридического текста — безопасно.
Находки — по периметру: отсутствие CSP, безусловная загрузка стороннего скрипта Telegram без SRI.

## 🟡 Средний приоритет

### 1. Скрипт `telegram-web-app.js` грузится безусловно для ВСЕХ посетителей (включая чистый PWA-режим), без Subresource Integrity

> ✅ **Исправлено — выбран вариант (b), устраняющий загрузку целиком, а не просто SRI.** Статичный
> `<script src="...">` в `<head>` заменён на инлайн-скрипт: Telegram при запуске Mini App всегда
> добавляет initData как `#tgWebAppData=...` в `location.hash` ДО начала загрузки страницы —
> синхронно доступный, надёжный признак «мы реально внутри Telegram», не требующий самого SDK.
> Скрипт telegram.org подгружается через `document.write` (безопасно и без warning'а — выполняется
> синхронно во время начального парсинга `<head>`, не после `load`) ТОЛЬКО когда этот маркер
> присутствует; для обычных PWA-посетителей сторонний код теперь не загружается вовсе — атака
> через компрометацию CDN Telegram для них неприменима в принципе. `integrity=`/SRI сознательно НЕ
> добавлен: у Telegram нет официально публикуемого хеша для этого файла, он меняется вместе с
> релизами SDK — захардкоженный хеш сломал бы Mini App при первом же обновлении без синхронного
> процесса его освежения (риск ложного срабатывания перевешивает пользу без такого процесса).
> `crossorigin="anonymous"` добавлен. Пункт (c), CSP — см. находку 2.

- **Где:** `FamilyHub.Web/src/index.html:17`
  `<script src="https://telegram.org/js/telegram-web-app.js"></script>`
- **Проблема:** этот `<script>` — в `<head>`, вне какого-либо условия — выполняется для КАЖДОЙ
  загрузки страницы, включая обычных PWA-пользователей, которые никогда не открывают приложение
  внутри Telegram. У тега нет атрибута `integrity`/`crossorigin` (Subresource Integrity) — браузер
  выполнит содержимое файла, каким бы оно ни было на момент запроса к `telegram.org`, без проверки
  хеша.
- **Почему это важно:** доверие полностью выносится на `telegram.org` и на канал HTTPS без
  дополнительной проверки целостности. Если у Telegram когда-либо будет скомпрометирован именно
  этот файл на CDN (supply-chain инцидент, не обязательно взлом самого FamilyHub) — скрипт получит
  полный доступ к DOM/JS-контексту PWA, включая переменные в памяти, non-httpOnly-хранилища
  (`localStorage`, где, к слову, лежит `familyhub:devTgId`), и сможет инициировать запросы к API
  FamilyHub от имени залогиненного пользователя (httpOnly cookie сам по себе не прочитать, но
  запрос с `withCredentials` инициировать можно).
- **Рекомендация:** (a) добавить `integrity="sha384-..."` + `crossorigin="anonymous"`, если контент
  скрипта достаточно стабилен между релизами Telegram (стоит проверить, насколько часто меняется);
  (b) рассмотреть загрузку скрипта только когда приложение реально определено как открытое внутри
  Telegram (сложнее, т.к. до загрузки скрипта это неизвестно клиенту — возможный компромисс:
  грузить `async`/`defer` и не блокировать остальное приложение); (c) в любом случае — добавить
  `Content-Security-Policy` (см. находку №2), которая ограничит, что этот (или любой другой)
  скрипт сможет сделать, даже если будет скомпрометирован.

### 2. Нет `Content-Security-Policy` — ни в виде meta-тега, ни (судя по бэкенду) в виде заголовка

> ✅ **Исправлено на бэкенде** (заголовок надёжнее meta-тега: работает для `frame-ancestors`,
> покрывает случай, когда HTML ещё не распарсен). Новая middleware в `Program.cs` (сразу после
> `UseStaticFiles`, до `UseAuthentication`) выставляет `Content-Security-Policy` для всех ответов,
> кроме `/hangfire` и `/dev/*` (dev-only инструменты со своими инлайн-скриптами без CSP-нонсов —
> не часть фронтенда, ломать их незачем): `default-src 'self'; script-src 'self' https://
> telegram.org; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self';
> connect-src 'self'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action
> 'self'`. `style-src` требует `'unsafe-inline'` — Angular без CSP-nonce вставляет
> component-стили инлайново, это ожидаемое ограничение платформы, не недоработка. Заодно добавлены
> `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`,
> `X-Frame-Options: DENY` (fallback на frame-ancestors для старых браузеров) — закрывает и
> [09-config-deployment, находка 3]. Проверено вручную: `curl` подтвердил заголовок на `/`
> (SPA) и на `/api/*`, отсутствие на `/hangfire`; шрифты/иконки/скрипты Angular — все
> same-origin (бандлятся из `node_modules`, внешних CDN в `angular.json` нет), единственный
> внешний источник — уже заранее разрешённый `telegram.org`. Полную in-browser проверку (нулевые
> CSP-violation в консоли на реальной production-сборке) не проводил — в этой сессии нет
> браузерного инструмента; в docker-compose dev-стенде страницу отдаёт Vite/`ng serve`
> (не бэкенд), поэтому CSP-заголовок там не действует вовсе — стоит проверить вручную один раз
> на реальной сборке, обслуживаемой бэкендом.

- **Где:** `FamilyHub.Web/src/index.html`, `Api/Program.cs` (нет добавления заголовков ответа,
  кроме явного `Cache-Control`/`Pragma` для `/api/*`).
- Отсутствие CSP — не находка сама по себе (многие проекты сознательно не используют CSP на раннем
  этапе), но в сочетании с пунктом №1 (сторонний скрипт без SRI) существенно снижает «второй рубеж
  обороны» на случай XSS откуда угодно (в т.ч. через будущие уязвимости в зависимостях). Стоит
  рассмотреть хотя бы базовую политику (`default-src 'self'; script-src 'self'
  https://telegram.org; object-src 'none'; frame-ancestors 'none'`) на уровне реверс-прокси/edge
  (см. также [09-config-deployment], где этот же пункт поднимается для бэкенда).

## 🟢 Низкий приоритет / на заметку

### 3. `DevPanelComponent` корректно гейтится `isDevMode()`, но зависит от того, что сборка реально помечена production

> ✅ **Подтверждено как процессная находка — действий в коде не требовалось.** `isDevMode()` —
> штатный compile-time флаг Angular, вырезаемый при `ng build --configuration production`; код
> компонента корректен. CI/CD-конфигурации в репозитории не найдено (нет `.github/workflows` и
> аналогов) — подтвердить «деплой всегда собирается с production-конфигурацией» на уровне
> процесса не из чего; фиксируется как эксплуатационное напоминание для того, кто настраивает
> реальный деплой.

### 4. `TelegramService.getDevTelegramId()` читает и сохраняет `?devTgId=` в `localStorage` во ВСЕХ сборках, не только dev

> ✅ **Исправлено.** `getDevTelegramId()` теперь начинается с `if (!isDevMode()) return null;` —
> тот же compile-time гейт, что и у `DevPanelComponent`, вырезаемый в production-сборке. Случайный
> `?devTgId=...` в проде больше не читается и не сохраняется в `localStorage` даже до того, как
> серверная проверка (`DevAuthenticationHandler`) успела бы его отклонить.

- **Где:** `app/services/telegram.service.ts:50-57`.

### 5. `bypassSecurityTrustHtml` — использование безопасно, но стоит зафиксировать инвариант явно

> ✅ **Исправлено — инвариант зафиксирован явно в коде, на каждом из четырёх мест.** Комментарии
> у всех вызовов (`consent-gate.component.ts`, `consent-text.component.ts`, `login.component.ts`,
> `privacy.component.ts`) переписаны с нейтрального «доверенный HTML» на явное
> `ИНВАРИАНТ: ... безопасен ТОЛЬКО пока ... не редактируемый пользователем/админкой контент`,
> с указанием, что нужно сделать, если инвариант перестанет выполняться (санитизация встроенным
> Angular-санитайзером вместо bypass, либо серверная санитизация редактируемого HTML). Ссылка на
> эту находку добавлена в каждый комментарий.

- **Где:** `consent-gate.component.ts:36`, `consent-text.component.ts:36`, `login.component.ts:236`,
  `privacy.component.ts:29` — все четыре получают HTML исключительно из
  `AuthService.getConsentText()`/аналогичных вызовов, которые в конечном счёте читают embedded-ресурс
  на бэкенде (`ConsentService.LoadLegalText`), не пользовательский ввод.

## ✅ Проверено, проблем не найдено

- `authInterceptor` — корректно различает Telegram/dev-режим (заголовки) и PWA-режим (cookie +
  `withCredentials`), дедуплицирует параллельные `/api/auth/refresh` через общий `refreshInFlight`
  промис, не пытается рефрешить сессию на заведомо session-less путях (`SESSION_LESS_AUTH_PATHS`) —
  предотвращает потенциальный бесконечный цикл на `/refresh` самом по себе.
- `authGuard`/`consentGuard` — корректно разводят Telegram-режим (проверка привязки TelegramId) и
  PWA-режим (проверка `me()`), не блокируют друг друга при отсутствии аутентификации.
- Экспорт данных (`exportAccountData`) сознательно переведён с `window.open`/прямой ссылки на
  `HttpClient`-запрос — в коде явно объяснено, почему (иначе Telegram-режим не получал бы
  Authorization-заголовок интерцептора при обычной навигации браузера) — корректное решение
  реальной проблемы, не заплатка.
