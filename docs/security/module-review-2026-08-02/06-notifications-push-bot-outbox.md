# Модуль: Оповещения, Web Push, Telegram-бот, событийная шина (outbox)

**Файлы:** `Api/Features/Notifications/*`, `Api/Features/Push/*`, `Api/Features/Bot/*`,
`Infrastructure/Notifications/*`, `Infrastructure/Outbox/*`, `Infrastructure/Telegram/*`
(в части бота)

**Статус:** 🟢 1/3 закрыта (находка 3 — см. пометку ✅; №1, №2 — уже сознательно
задокументированные компромиссы, действий не требовалось).

## Сводка

Событийная шина (outbox → MediatR, с изолирующим паблишером и backoff-ретраями) и доставка
оповещений (Telegram/Web Push, фан-аут по независимым каналам с per-user предпочтениями) сделаны
надёжно: сбой одного хендлера/канала не топит остальные, идемпотентность через `DedupKey`,
webhook бота проверяется constant-time сравнением секрета до разбора тела. Явных находок средней
степени тяжести не появилось — только точки для проверки на будущее.

## 🟢 Низкий приоритет / на заметку

### 1. `OutboxMessage.Payload` может содержать ПДн, хранится 7 дней после обработки

- **Где:** `Infrastructure/Outbox/OutboxOptions.cs:20-24` (`ProcessedRetention = 7 дней`,
  `PurgeInterval = 1 час`).
- Уже осознанно задокументировано в самом коде («Payload — снимок события и может содержать ПДн...
  поэтому обработанное не живёт дольше срока диагностики (152-ФЗ)») — не находка, а подтверждение,
  что 7-дневное окно — сознательный компромисс между диагностикой сбоев и минимизацией хранения.
  Фиксируется здесь только для полноты (проверялось специально, т.к. это первое место, где
  «сырые» события с потенциальными ПДн лежат дольше одной транзакции).

### 2. Web Push payload корректно не содержит `Title`/`Body` — но стоит перепроверить при появлении новых типов оповещений

- **Где:** `Infrastructure/Notifications/WebPushNotificationSender.cs:81-87` (`BuildPayload`) —
  всегда шлёт обобщённый «Новое уведомление», реальный контент открывается только после клика,
  через уже аутентифицированный `/api/notifications`. Соответствует ADR-0004. Не находка — фиксация
  того, что при добавлении новых каналов/типов оповещений эту гарантию стоит держать в уме и не
  начать случайно прокидывать `notification.Title`/`Body` в push-payload «для красоты».

### 3. Ежедневный ретрай-свип (`ReminderScanJob.SendPendingAsync`) не ограничен по возрасту

> ✅ **Исправлено.** Новая опция `NotificationOptions.RetrySweepMaxAgeDays = 7` (по умолчанию) —
> `SendPendingAsync` теперь берёт только строки `SentAt == null && CreatedAt >= today - 7 дней`.
> Окно в 7 дней выбрано с запасом: переживает многодневный сбой канала (истёкший VAPID/Bot Token
> — обычно замечается и чинится за пару дней), но не долбит в мёртвый канал неделями и не
> доставляет давно устаревшее «скоро истекает». Заодно добавлена наблюдаемость: количество
> исключённых из свипа устаревших строк логируется как `Warning` на каждый прогон (если > 0) —
> раньше затяжной сбой канала остался бы полностью незаметным в логах.
>
> Уточнение по факту чтения кода: механизм накопления, описанный выше («канал стабильно
> недоступен → строки копятся»), на практике не совсем так работает — `NotificationSendingService.
> TrySendAsync` проставляет `SentAt` БЕЗУСЛОВНО после попытки (успешной или нет, см. докстринг
> метода), поэтому сбой конкретного канала сам по себе не оставляет `SentAt == null`. Реальный
> (более узкий) сценарий — сбой самого `SaveChangesAsync` в конце `SendPendingAsync`/`NotifyAsync`
> (например, временная недоступность БД во время записи), из-за которого ВЕСЬ обработанный за
> прогон батч останется `SentAt == null` и уйдёт в ретрай назавтра. Возрастной cutoff — здравая
> защита независимо от точного механизма, поэтому фикс применён как есть.
>
> Покрыто тестами (`ReminderScanJobTests.RunAsync_PendingNotificationOlderThanRetryWindow_...`,
> `..._WithinRetryWindow_...`, `..._CustomRetrySweepMaxAgeDays_...`).

## ✅ Проверено, проблем не найдено

- `BotEndpoints.IsValidSecret` — сравнение секрета вебхука через `CryptographicOperations.
  FixedTimeEquals`, fail-closed при пустом `Telegram:WebhookSecret` (возвращает `false`, а не
  пропускает) — проверяется ДО разбора тела запроса.
- `IsolatingLoggingPublisher` — сбой одного MediatR-хендлера не блокирует доставку события
  остальным подписчикам (в отличие от дефолтного `ForeachAwaitPublisher`); ошибки агрегируются и
  сигналят `OutboxProcessor` о необходимости ретрая всей строки — корректная семантика at-least-once.
- `NotificationSendingService.AddIfNewAsync` — идемпотентная вставка через `UNIQUE(DedupKey)` с
  корректной обработкой гонки (`DbUpdateException` → detach только своей записи, не всего
  ChangeTracker'а — важно, т.к. `AppDbContext` шарится с `OutboxProcessor` в рамках одного scope).
- `TelegramNotificationSender`/`WebPushNotificationSender` — сбой одной подписки/одного канала не
  прерывает остальные (свой `try/catch` на каждую попытку), протухшие Web Push подписки (404/410 от
  релея) корректно вычищаются.
- Rate-limit на выдачу email-кодов и кодов привязки — переиспользует общий `EmailOtpService`,
  разница только в `EmailCodePurpose` — нет отдельного, менее защищённого пути для Telegram-привязки.
