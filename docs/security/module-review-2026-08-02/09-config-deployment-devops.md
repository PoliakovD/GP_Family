# Модуль: Bootstrap (Program.cs), docker-compose, env-файлы, деплой

**Файлы:** `Api/Program.cs` (инфраструктурная часть — хостинг/pipeline, не бизнес-фичи, они
разобраны в соответствующих модулях), `docker-compose.yml`, `.env.example`, `prod.env` (только

**Статус:** 🔴 1/1 закрыта, 🟡 3/3 закрыты (находки 1, 2, 3 — см. пометки ✅; №3 закрыта частично,
`UseHsts()` сознательно оставлен — зависит от подтверждения по реверс-прокси). 🟢 находки 4-6 —
либо не требуют действий, либо вне скоупа кода (проверка процесса деплоя).

## Сводка

`Program.cs` последовательно применяет fail-fast для всех критичных секретов (JWT-ключ, ключ
шифрования, ключ подписи ссылок на скачивание, ключи провайдеров обогащения) — хорошая практика,
ошибка конфигурации падает при старте, а не тихо на первый запрос. Основная находка — этот
fail-fast эффективно обходится в `docker-compose.yml` за счёт захардкоженного fallback-значения
ключа шифрования. Второй пласт находок — рассинхронизация `.env.example` с реальными требуемыми
переменными.

## 🔴 Высокий приоритет

### 1. Захардкоженный fallback ключа шифрования в `docker-compose.yml`, закоммиченный в git

> ✅ **Исправлено, закрыто жёстче, чем предложено в рекомендации.** `docker-compose.yml`:
> дефолт заменён на `${ENCRYPTION_MASTER_KEY:?...}` (Compose отказывается стартовать без явного
> значения в `.env`, с понятным сообщением). Дополнительно — то, чего не было в исходной
> рекомендации: сам fallback-ключ (`MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=`) оставался бы
> актуальным дефолтом ещё и через `appsettings.Development.json`, поэтому убрали его И оттуда —
> секреты (`Encryption:MasterKey`, `Jwt:SigningKey`, `Attachments:DownloadSigningKey`) теперь
> нигде не хардкодятся, тянутся из env даже в Development. `Program.cs` дополнительно отказывается
> стартовать вне Development, если каким-то путём подставлен именно этот исторический ключ
> (defense in depth — значение всё равно навсегда осталось в истории git). Тестовые фабрики
> (`FamilyHubWebFactory`, `BotWebhookWebFactory`) теперь явно задают тестовые значения через
> `UseSetting`, не полагаясь на файл конфигурации.

- **Где:** `docker-compose.yml` (сервис `api`):
  ```yaml
  # Dev-ключ шифрования медданных (тот же, что в appsettings.Development.json).
  Encryption__MasterKey: "${ENCRYPTION_MASTER_KEY:-MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=}"
  ```
- **Проблема:** `Program.cs:86-88` делает fail-fast, если `Encryption:MasterKey` пуст — но
  через `docker-compose.yml` переменная НИКОГДА не приходит пустой: если `ENCRYPTION_MASTER_KEY`
  не задан в `.env` (а его там и не может быть задан по шаблону — см. находку №2, эта переменная
  вообще отсутствует в `.env.example`), Compose подставляет дефолт из самого файла — строку
  `MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=`, которая декодируется в предсказуемый ASCII-паттерн
  `0123456789abcdef0123456789abcdef` (32 байта). Это значение лежит в открытом виде в
  публичной/приватной истории git, доступно любому, у кого есть доступ к репозиторию.
- **Почему это важно:** задуманный fail-fast («ключ шифрования обязателен, иначе не запускаемся»)
  из `Program.cs` фактически не срабатывает при запуске через `docker compose up` без явно
  настроенного `.env` — вместо явной ошибки конфигурации приложение тихо стартует и начинает
  шифровать все ПДн (мед-записи, ФИО в днях рождения, имена файлов вложений, ключи Web Push
  подписок) известным из исходников ключом. Смягчающие факторы: сам файл называется частью dev-
  окружения (`Dockerfile.dev`, `ASPNETCORE_ENVIRONMENT: Development` захардкожен в этом же файле),
  и существует отдельный `prod.env` с реальным набором переменных, включая `Encryption__MasterKey`
  без плейсхолдера — то есть штатный путь в прод, похоже, НЕ использует этот `docker-compose.yml`
  напрямую. Тем не менее сам факт наличия такого «тихого» фолбэка — системный риск: он
  сработает для ЛЮБОГО окружения, поднятого через `docker compose up` без вдумчивого чтения этого
  конкретного файла (staging, демо-стенд, чей-то персональный "quick test с реальными данными" и
  т.п.).
- **Рекомендация:** убрать дефолтное значение из `docker-compose.yml` полностью — пусть при
  отсутствии `ENCRYPTION_MASTER_KEY` в `.env` подстановка `${ENCRYPTION_MASTER_KEY}` останется
  пустой строкой, и тогда сработает штатный fail-fast из `Program.cs`, как и задумано. Если ключ
  для чистого локального dev действительно нужен «из коробки» без лишних шагов — сгенерировать его
  один раз и положить именно в `.env.example` (или сопроводить `README`/`make dev` шагом
  генерации), а не в `docker-compose.yml`, который попадает в git безусловно.

## 🟡 Средний приоритет

### 2. `.env.example` не соответствует реальным требуемым переменным — расходится с `prod.env`

> ✅ **Исправлено.** `.env.example`: добавлены `ENCRYPTION_MASTER_KEY` и
> `Attachments__DownloadSigningKey` (реально используемая переменная), убран мёртвый
> `LocalFileStorage__SigningKey`. Заодно добавлен явный fail-fast для
> `Attachments:DownloadSigningKey` в `Program.cs` (раньше `DownloadTokenService.Sign` падал
> лениво только при первой выдаче ссылки) — закрывает и второй риск, описанный в разделе
> «Почему это важно» этой находки.

- **Где:** `.env.example:70` содержит `LocalFileStorage__SigningKey=CHANGE_ME_min_32_chars` —
  но `LocalFileStorageOptions` (`Infrastructure/Storage/LocalFileStorageOptions.cs`) НЕ ИМЕЕТ
  свойства `SigningKey` вообще (только `RootPath`) — эта переменная ни на что не влияет и является
  «мёртвым» плейсхолдером. Настоящий ключ, который реально используется
  (`DownloadTokenService`/`AttachmentDownloadOptions.DownloadSigningKey`, секция `Attachments`),
  в `.env.example` вообще не упомянут. `Encryption__MasterKey` также отсутствует в
  `.env.example` (при этом присутствует и в `prod.env`, и как fallback в `docker-compose.yml` —
  см. находку №1).
- **Почему это важно:** разработчик, честно следующий `.env.example` (копирует в `.env`, заменяет
  все `CHANGE_ME`), НЕ настроит `Attachments__DownloadSigningKey` — и получит не понятную ошибку
  при старте (fail-fast для этого ключа нет — `DownloadTokenService.Sign` бросает исключение лениво,
  только при первой попытке выдать ссылку на скачивание вложения), а для `Encryption__MasterKey`
  автоматически (и незаметно) съедет на захардкоженный dev-фолбэк из находки №1, даже не подозревая
  об этом.
- **Рекомендация:** сверить `.env.example` построчно с `prod.env` (только по именам ключей, без
  копирования значений) и актуальными `*Options`-классами, убрать неиспользуемые записи, добавить
  отсутствующие обязательные.

### 3. Заголовки безопасности (CSP/HSTS/X-Frame-Options/X-Content-Type-Options) не настроены в `Program.cs`

> ✅ **Исправлено — часть заголовков.** Новая middleware в `Program.cs` (см.
> [08-web-frontend, находка 2](08-web-frontend-angular.md)) выставляет `Content-Security-Policy`,
> `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY` для всех ответов
> кроме `/hangfire`/`/dev/*`. `UseHsts()` НЕ добавлен намеренно — не проверено, есть ли перед
> приложением реверс-прокси/edge, терминирующий TLS (см. находку 6 ниже, тот же вопрос); включать
> HSTS без ясности по этому пункту рискованно (неверный `Strict-Transport-Security` может залочить
> пользователей на HTTPS раньше, чем инфраструктура готова его гарантированно отдавать). Оставлено
> как отдельное решение, требующее подтверждения по деплою.

- **Где:** `Api/Program.cs` — нет `UseHsts()`, нет middleware, добавляющего заголовки ответа, кроме
  явного `Cache-Control`/`Pragma` для `/api/*` (строки 494-502).
- Возможно, эти заголовки добавляются на уровне реверс-прокси/edge (nginx/Caddy/облачный балансир)
  вне этого репозитория — не проверялось, т.к. конфигурация прокси не найдена в кодовой базе.
  Фиксируется как пункт, требующий явного подтверждения: если заголовки НИГДЕ не выставляются,
  сайт отдаётся без CSP, без `X-Frame-Options`/`frame-ancestors` (риск clickjacking для страницы
  логина), без `X-Content-Type-Options: nosniff`. См. также [08-web-frontend, находка №2].

## 🟢 Низкий приоритет / на заметку

### 4. Dev-only сервисы в `docker-compose.yml` — открытые порты, слабые дефолтные креды, `SEQ_NO_AUTH=true`

- **Где:** `docker-compose.yml` — Postgres/MinIO/Seq пробрасывают порты на хост
  (`${POSTGRES_PORT}`/`${MINIO_API_PORT}`/`${MINIO_CONSOLE_PORT}`/`${SEQ_PORT}`), `.env.example`
  задаёт тривиальные креды (`postgres`/`postgres`, `minioadmin`/`minioadmin`), Seq по умолчанию
  без аутентификации (`SEQ_NO_AUTH=true`).
- Ожидаемо и разумно для локальной разработки; фиксируется только как явное напоминание, что этот
  конкретный `docker-compose.yml` категорически не должен становиться основой прод-конфигурации
  «копипастой» (в т.ч. потому что в нём же — находка №1).

### 5. `/hangfire` дашборд и `/dev/*` эндпоинты без авторизации — но корректно закрыты `IsDevelopment()`

- **Где:** `Api/Program.cs:526-585`.
- Дашборд Hangfire монтируется с `Authorization = Array.Empty<IDashboardAuthorizationFilter>()`
  (полностью открыт), но весь блок обёрнут в `if (app.Environment.IsDevelopment())`. То же для
  `/dev/trigger-*` и `/dev/email-preview/*`. Код корректен — риск целиком переносится на
  эксплуатационную практику: если в реальном проде `ASPNETCORE_ENVIRONMENT` когда-либо окажется
  не `Production` (опечатка, забытая переменная окружения на хосте) — все эти маршруты, включая
  возможность вручную запускать джобы и полностью открытый Hangfire dashboard (история задач,
  возможность их удалять/перезапускать), станут доступны анонимно из интернета. Стоит явно
  зафиксировать (вне кода — в процессе деплоя/чеклисте) обязательную проверку
  `ASPNETCORE_ENVIRONMENT=Production` на реальном хосте.

### 6. Нет `UseHttpsRedirection()`/`UseHsts()` в `Program.cs`

- Как и в находке №3 — вероятно, TLS-терминация и редирект на HTTPS делаются на уровне
  реверс-прокси перед приложением. Фиксируется для явного подтверждения (не проверялось — прокси
  вне репозитория).
