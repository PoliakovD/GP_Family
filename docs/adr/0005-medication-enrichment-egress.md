# ADR-0005. Внешний веб-поиск для обогащения справочника: исключение из egress-политики ADR-0001

**Статус:** принят (этап 4). **Дата:** 2026-07-30.

## Контекст

`kb.global_medications_kb` (задача 2.6) — обезличенный общий справочник препаратов: назначение,
условия хранения, влияние на вождение. До этапа 4 таблица существовала как пустая схема — писателя
не было (см. `KbIsolationGuardTests.PersonalContext_CannotBeStoredInKbRow`, явно ожидающий
«будущий writer-сервис этапа 4»).

Наполнить справочник знаниями о конкретном препарате без выхода в интернет невозможно — ни ГРЛС,
ни Vidal/RLS не доступны локальному Qwen. Значит нужен исходящий HTTP-вызов к внешнему поисковому
API, а ADR-0001 задаёт egress как явный allowlist (deny by default) и по своему же чек-листу
требует для любой новой исходящей зависимости отдельного решения — «сервис размещён в РФ? проходит
ли через него ПДн?» — прежде чем добавлять правило.

## Решение

1. **Наружу уходит ТОЛЬКО нормализованное название препарата.** `MedicationNameNormalizer.Normalize`
   (см. `src/FamilyHub.Infrastructure/Search/MedicationNameNormalizer.cs`) приводит «Парацетамол
   400мг таб. №20» к «парацетамол» ещё до похода в сеть — ни user/family-идентификаторов, ни
   любого другого персонального контекста в запросе нет. Это не ПДн о конкретном человеке: одно и
   то же название ищется независимо от того, кто и в какой семье его сохранил.
2. **Один запрос на препарат — глобально, не на пользователя.** Дедуп на уровне БД (частичный
   уникальный индекс `MedicationEnrichmentJobs.NormalizedName` среди `Pending`/`Running` задач, см.
   `MedicationEnrichmentJobConfiguration`) — если два человека из разных семей сохраняют «Ибупрофен»
   почти одновременно, внешний запрос уходит один раз. Повторная проверка kb внутри
   `MedicationEnrichmentProcessor` перед самим запросом устраняет и более редкую гонку.
3. **Асинхронная очередь развязывает запрос во времени с действием пользователя.** Обогащение идёт
   фоновой Hangfire-задачей в выделенной очереди `enrichment` (см. `Program.cs`,
   `MedicationEnrichmentProcessor`), а не синхронно внутри HTTP-запроса сохранения медикамента —
   нет прямой корреляции «конкретный человек в конкретный момент запросил конкретное название»,
   наблюдаемой третьей стороной по трафику.
4. **Провайдер — за абстракцией, переключается конфигом.** `IMedicationSearchProvider`
   (`src/FamilyHub.Infrastructure/Enrichment/`): `NullMedicationSearchProvider` — провайдер по
   умолчанию, наружу не уходит ничего; `BraveSearchProvider` (США) реализован как альтернатива, но
   **не используется по умолчанию**; активный провайдер — `YandexSearchProvider` (Yandex Cloud Web
   Search API, `v2/gen/search`, GenSearch) — РФ-хостинг, egress-исключение по-прежнему нужно (новый
   исходящий HTTP-вызов к внешнему API — само по себе основание для этого ADR, даже когда сервис в
   РФ-юрисдикции), но снимается часть риска, ради которой ADR-0001 вообще требует отдельного
   решения («иностранная юрисдикция? проходит ли ПДн?» — здесь юрисдикция РФ).
5. **Фильтрация по доверенным доменам — на нашей стороне, постфактум, для обоих провайдеров.**
   `EnrichmentOptions.TrustedDomains` (по умолчанию `grls.rosminzdrav.ru`, `vidal.ru`, `rlsnet.ru`).
   Для Yandex GenSearch пробовали жёстко ограничить сам поиск через поле `host` (`host.host`
   в теле запроса) — на практике живой запрос с этим полем стабильно возвращал
   `isAnswerRejected: true` ("Ничего не найдено"), хотя без ограничения те же домены (например
   `rlsnet.ru`) находятся и попадают в `used: true`. Похоже, GenSearch разбивает запрос на
   несколько под-запросов внутри себя, и узкий `host`-список не даёт найти релевантные документы
   сразу для всех них. Поэтому оставили тот же приём, что и у Brave: запрос без сужения, фильтр
   по `used && TrustedDomains` — на нашей стороне, постфактум. Список доверенных источников
   остаётся под нашим контролем в обоих случаях, а не зависит от того, что решил вернуть провайдер.
6. **Скрейпинг страниц не делаем.** Brave отдаёт сниппет выдачи (`description`) на каждый источник;
   Yandex GenSearch — уже сгенерированный ответ (`message.content`) вместе со списком источников и
   флагом `used` (какие реально использованы). Ни в одном случае мы не ходим на сами страницы —
   меньше исходящего трафика, не ломается от смены вёрстки источника.
7. **Суммаризация остаётся строго на локальном Qwen (ADR-0001 п.2 не пересматривается) — даже
   когда провайдер уже прислал сгенерированный ответ.** `MedicationSummarizer` вызывает
   `ILmStudioJsonClient` (тот же локальный LM Studio, что и OCR) над материалом ЛЮБОГО провайдера —
   Yandex GenSearch — не исключение: его `message.content` — сырой материал для локальной
   суммаризации под нашим антигаллюцинационным гейтом и нашей схемой `MedicationSummary`, а не
   готовый текст, который пишется в справочник напрямую. Облачный сервис не становится соавтором
   строки `kb.global_medications_kb`.
8. **Антигаллюцинационный гейт — не про egress, но напрямую про доверие к данным справочника.**
   Если суммаризатор не сослался ни на один сниппет (`usedSourceIndexes` пуст) — запись в
   `kb.global_medications_kb` не создаётся, задача уходит в `Failed`. Способ применения/дозы
   (`MedicationSummary.Usage`, схема v2) и противопоказания/рекомендации (`SpecialNotes`) — в
   объёме, что есть в цитируемой официальной инструкции, извлекаются как обычные разделы
   справочника, а НЕ ограничиваются белым списком полей: это позиция продукта (не ограничивать
   модель, отдавать пользователю максимум пользы из уже проверенных источников), а не отступление
   от гейта — заземление на `usedSourceIndexes`/`TrustedDomains` остаётся обязательным для любого
   поля. Персонализированного подбора дозы под конкретного человека здесь никогда не было и не
   может быть физически (конвейер не получает возраст/вес/диагноз пользователя) — именно это,
   а не общая информация из инструкции, было бы медицинской консультацией и требовало бы пересмотра
   `task-5.1-medications.md` (та задача — про отдельную функцию проверки совместимости препаратов,
   не про эту). Дисклеймер «не медицинская консультация» — в UI (`KbCardComponent`), не в
   ограничении содержания.
9. **Вентиль в Postgres, не месячная квота.** *(Третья редакция этого пункта — история решений
   здесь честно ведётся, а не переписывается. Изначально — `EnrichmentQuotaService`, удалён в
   промежуточном рефакторинге, квота какое-то время нигде не проверялась (`EnrichmentJobStatus.
   Skipped` временно был неиспользуемым значением). Вторая редакция вернула квоту как
   `WebSearchQuotaService.MonthlyQuotaExceededAsync` — считала строки `WebSearchCallLog` за
   календарный месяц с `Outcome != CacheHit`, превышение → `Skipped` без ретрая. Убрана
   окончательно: месячный лимит на глаз плохо предсказывал реальный грантовый бюджет облачного
   провайдера поиска (см. прогрев кэша ниже), а превышение просто ТЕРЯЛО задачу — `Skipped`
   терминален, никто её не возобновлял.)* Сейчас — `IWebSearchValveService` (единственная строка
   `WebSearchConfig`, читается БЕЗ кеша — см. её class doc: закрытие вентиля должно остановить
   платные вызовы В ЭТУ ЖЕ секунду, TTL-кеш здесь недопустим) плюс отдельный, явно заданный
   бюджет платных вызовов на конкретный прогон прогрева (`SearchWarmupRun.MaxPaidCalls`) — оба
   параметра админ ставит осознанно под конкретную ситуацию, не под усреднённый "лимит в месяц".
   Проверяется в начале каждого из трёх enrich-процессоров, ПЕРЕД реальным вызовом `SearchAsync`
   (после проверки кэша — свежий кэш вентилем не гейтится). Закрытый вентиль НЕ прерывает задачу
   терминально — переводит в `EnrichmentJobStatus.Deferred` («жива, просто ждёт»), и
   `DeferredEnrichmentReleaseJob` автоматически возобновляет все такие задачи при открытии
   вентиля. `Skipped` остаётся в enum как легаси-значение для строк, записанных до этой правки —
   новым задачам больше не присваивается.

## Egress-allowlist (дополнение к ADR-0001 п.3)

Правило добавляется в инфраструктурный allowlist наравне с `api.telegram.org` (ADR-0001) и
push-релеями (ADR-0004), активный на сегодня хост: **`searchapi.api.cloud.yandex.net`, только
исходящий HTTPS, только пока `Enrichment:Provider=Yandex`.** `api.search.brave.com` остаётся
в allowlist как поддерживаемая, но не используемая по умолчанию альтернатива (переключение —
только конфигом `Enrichment:Provider`, без правки кода). При `Provider=Null` (провайдер по
умолчанию в `.env.example`; в реальном `.env` дев-окружения активен `Yandex`) ни одно из этих
правил не задействуется — `NullMedicationSearchProvider` не открывает соединений.

## Расширение на справочник лабораторных показателей (ветка medicalrecords)

Тот же egress-канал (`searchapi.api.cloud.yandex.net`/`api.search.brave.com`, тот же
`IMedicationSearchProvider`, переключаемый `Enrichment:Provider`) теперь наполняет и второй
обезличенный справочник — `kb.global_lab_analytes_kb` (референсные диапазоны/пояснения к
лабораторным показателям, зеркало конвейера выше: `LabAnalyteEnrichmentProcessor` →
`LabAnalyteKbSummarizer` → `LabAnalyteKbWriter`). Решения 1-9 применяются без изменений — наружу
уходит только нормализованное имя показателя (`LabAnalyteNormalizer.Normalize`), тот же дедуп по
`LabAnalyteEnrichmentJobs.NormalizedName`, тот же антигаллюцинационный гейт
(`LabAnalyteKbSummarizer` требует `usedSourceIndexes`). Два уточнения:

- **Доверенные домены — отдельный список**, `EnrichmentOptions.AnalyteTrustedDomains` (по
  умолчанию `helix.ru`, `invitro.ru`, `gemotest.ru`, `kdlmed.ru`, `cmd-online.ru`) — реестры
  лекарств (`TrustedDomains`) бесполезны для референсных диапазонов анализов. Провайдер выбирает
  список и формулировку запроса по параметру `WebSearchTopic` (`Medication`/`LabAnalyte`).
- **Вентиль — общий на все три конвейера** (`IWebSearchValveService.IsPausedAsync`, одна строка
  конфига, не привязана к конкретной таблице задач) — все три делят одного и того же внешнего
  провайдера, отдельный вентиль на конвейер позволил бы одному продолжать платить, пока админ
  думает, что остановил всё разом.

## Аудит платных вызовов (`WebSearchCallLog`, добавлено при батч-загрузке документов)

До появления этой таблицы восстановить «сколько заплачено и за что» было нельзя — единственным
следом были `job.ExternalSearchAt`/`Provider` и строка кэша (`kb.medication_search_cache`/
`kb.lab_analyte_search_cache`), которая хранит только ПОСЛЕДНИЙ результат по ключу и
перезаписывается при каждом обновлении. `WebSearchCallLog` (схема `public`, не персональные
данные — см. п.1 выше: наружу и так уходит только нормализованное название) — одна строка на
КАЖДЫЙ вызов `IMedicationSearchProvider.SearchAsync`, включая кэш-хиты (`WebSearchCallOutcome.
CacheHit`, единственное не платное значение — без него нельзя проверить, что кэш вообще
работает). Пишет `WebSearchCallLogger` в собственном `IServiceScopeFactory`-скоупе (провайдеры
вызываются из середины транзакции процессора — писать в тот же `AppDbContext` значило бы
закоммитить её раньше времени), сбой записи лога только логируется, не роняет сам поиск. Хранит
`QueryText` целиком — буквально то, что ушло провайдеру. Ретеншн — 180 дней (`AuditRetentionJob`,
короче основного 12-месячного окна доступа: это диагностика расходов, не 152-ФЗ-аудит). Админка —
«Операции → Журнал вызовов» (`/admin/operations/search-calls`; `AdminSearchCallsEndpoints`, `/api/admin/search-calls*`):
список с фильтрами (провайдер/тема/исход/период), полная карточка вызова, `/stats` — доля
кэш-хитов, расход текущего месяца и (если задана `Enrichment:PricePerPaidCall`) его денежная
оценка, состояние вентиля из п.9. Рядом — страница «Операции → Прогрев» (`AdminWarmupEndpoints`,
`/api/admin/enrichment/warmup*`): ручное насыщение кэша по списку названий, пока действует
грантовый лимит облачного провайдера — см. её class doc (`SearchCacheWarmupJob`) для устройства.

## Последствия

- Обновлён чек-лист/allowlist ADR-0001 п.3 — добавлен пункт «внешний поиск для обогащения
  справочника (см. ADR-0005)» как явное поименованное исключение, а не молчаливое расширение.
- Переход между Brave/Yandex — правка `Enrichment:Provider` в конфиге, оба класса
  `IMedicationSearchProvider` уже реализованы; смена активного провайдера не требует пересмотра
  решения целиком, только обновления активного хоста в этом разделе.
- Платный расход (для любого провайдера) идёт по проекту единицами-десятками в месяц (глобальный
  дедуп + повторная проверка kb + один воркер очереди `enrichment`) — не миллионами сохранений
  медикаментов по всем семьям; вентиль и бюджет прогона прогрева — единственные ограничители,
  оба ручные.
