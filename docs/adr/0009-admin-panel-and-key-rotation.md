# ADR-0009. Админ-панель и ротация ключей приложения

**Статус:** принят. **Дата:** 2026-08-25.

## Контекст

В проекте не было ни одной административной поверхности уровня платформы: «admin» означало
либо роль внутри конкретной семьи (`FamilyRole.Admin`, `docs/security/access-matrix.md`), либо
HTTP Basic на Hangfire/Swagger (`DevTools:AdminUser/AdminPassword`, `AdminBasicAuth`) поверх
периметра WireGuard/Caddy. Ни занятого места в S3, ни счётчиков пользователей, ни состояния
шины не было доступно без ручных SQL-запросов к боевой БД.

Более важная причина — ADR-0002 §5 описывал процедуру ротации мастер-ключа шифрования и
заканчивался словами «реализация отложена до появления второго ключа». Формат шифротекста уже
нёс `keyId` (`enc:{keyId}:{base64}` для полей, `FHE1|keyId|...` для файлов), но в процесс
загружался ровно один ключ, и оба шифра (`AesGcmFieldCipher`/`AesGcmFileCipher`) жёстко бросали
исключение при несовпадении `keyId`. Правка `Encryption:ActiveKeyId` была событием потери
данных. То же было верно для `Jwt:SigningKey` (`TokenValidationParameters.IssuerSigningKey` в
единственном числе — смена ключа мгновенно разлогинивала всех). Оба пункта числились в
`docs/security/module-review-2026-08-02/00-INDEX.md`, раздел «Отложено намеренно — нет
админки, чтобы это оформить иначе».

## Решение

### 1. Связка ключей вместо одного значения

Три независимых секрета приложения получили одинаковую модель: **активный** ключ (пишет новые
значения) + список **отставных** (только читают уже существующее). Формат ключей на диске не
менялся — ради этого `keyId` изначально закладывался в ADR-0002.

- **Encryption** (`IEncryptionKeyRing`/`EncryptionKeyRing`, `src/FamilyHub.Infrastructure/Security/`):
  `Encryption:ActiveKeyId`/`MasterKey` + `Encryption:PreviousKeys[].{Id,Material}`. Оба шифра
  резолвят ключ на чтение по `keyId`, зашитому в само значение/блоб, вместо жёсткого сравнения
  с единственным ключом процесса.
- **Jwt** (`JwtSigningKeyRing`, `src/FamilyHub.Infrastructure/Auth/Jwt/`): `Jwt:ActiveKeyId` +
  `Jwt:PreviousSigningKeys[].{Id,Material}`. `TokenService` подписывает активным и проставляет
  `kid`; `AddJwtBearer` переходит на `IssuerSigningKeys` (множественное число) — валидация
  пробует каждый ключ связки, не выбирает по `kid`. Уже выданный access-токен (живёт 15 минут
  по умолчанию) остаётся валиден весь свой TTL после смены активного ключа.
- **Attachments** (`DownloadTokenService`): `Attachments:PreviousSigningKeys[]` (без `Id` — HMAC-
  подпись ссылки не несёт keyId, проверка просто перебирает связку). Ссылка живёт 5 минут — самый
  дешёвый случай ротации, отставной ключ можно убирать почти сразу.

### 2. Фоновая перешифровка

Смена активного ключа шифрования немедленно делает связку читаемой (старые данные — по
отставному ключу), но НЕ перешифровывает существующие значения — это делает
`EncryptionRotationJob` (`src/FamilyHub.Infrastructure/Security/Rotation/`), Hangfire-очередь
`rotation` с `WorkerCount=1` (тот же приём, что у `enrichment`-очереди, ADR-0005) — гарантирует,
что одновременно исполняется не больше одной джобы.

Прогон описан строкой `EncryptionRotationRun` (схема `public` — инфраструктурное состояние, не
персональные данные), две резюмируемые фазы с курсором в самой строке (переживает рестарт
процесса):

1. **Поля** — `EncryptionRotationJob.FieldEntityTypes`, фиксированный список сущностей с
   `[Encrypted]`-свойствами (НЕ авто-обнаруживается сканом модели, в отличие от
   `AppDbContext.OnModelCreating` — курсору нужен стабильный порядок шагов). Каждая страница
   перезаписывается целиком (все `[Encrypted]`-свойства строки помечаются `IsModified`) —
   без попытки определить, какое именно свойство устарело: это потребовало бы читать сырой
   шифротекст в обход `IFieldCipher`, а лишняя перезапись уже-актуального значения безвредна
   (GCM-nonce и так меняется на каждую запись).
2. **Блобы вложений** — `FileAttachment.KeyId` (денормализованная колонка, миграция
   `AddFileAttachmentKeyId`, бэкфилл `v1` для всех существующих зашифрованных блобов на момент
   введения колонки) фильтрует страницы дёшево, без скачивания каждого объекта из MinIO ради
   заголовка `FHE1`.

Запуск — только по клику администратора (`AdminKeysService.StartOrResumeRotationAsync`,
`POST /api/admin/keys/encryption/rotate`; 409, если связка уже состоит из одного ключа — нечего
перешифровывать). Ночной добиватель (`encryption-rotation-catchup`, `0 4 * * *`) **никогда не
создаёт новый прогон сам** — только резюмирует уже идущий (`Status=Running`), если предыдущее
исполнение оборвалось (рестарт контейнера/редеплой, транзиентный сбой сети). Так опечатка в
конфигурации не может запустить перешифровку всех медданных без явного действия человека.

### 3. Отдельная аутентификация админ-панели

Новая секция `Admin:User/Password` (env `Admin__User`/`Admin__Password`), НЕ переиспользует
`DevTools:AdminUser/Password`: последняя пара защищает Hangfire/Swagger и по
`00-INDEX.md` планируется к удалению вместе с прочими dev-заглушками, тогда как админ-панель —
постоянная продуктовая поверхность с собственным жизненным циклом пароля.

`AdminAuthenticationHandler` (схема `AuthSchemes.Admin`) проверяет httpOnly-cookie
`familyhub.admin`, защищённую `ITimeLimitedDataProtector` (`IDataProtectionProvider`, уже
персистится в Postgres — сессия переживает редеплой). Схема **никогда** не участвует в
`AuthSchemes.Smart`-селекторе — подключается только явной политикой `PlatformAdmin` на группе
`/api/admin`, поэтому обычные PWA/Telegram-запросы её не видят вовсе, и cookie панели не
подменяет обычную identity пользователя.

### 4. Периметр: отдельный домен, не переиспользование существующего

`admin.{PUBLIC_DOMAIN}:4059` — новый Caddy-сайт, TLS `internal` (самоподписанный, как и
существующий класс служебных сайтов на `:8443`), Docker публикует контейнерный порт только на
`10.8.0.1` (WireGuard-адрес хоста), тем же host-IP-scoped приёмом, что и `:8443`. Порт
намеренно **отдельный** от `:8443` (Hangfire/Swagger, голый BasicAuth поверх периметра) — у
панели собственная аутентификация приложения, а не только периметр. С публичного домена `/admin*`
и `/api/admin/*` дополнительно заблокированы на уровне Caddy (`@blocked`, 404) — защита в
глубину поверх `AuthSchemes.Admin`, тот же принцип, что уже применён к `/hangfire*`/`/swagger*`.

SPA-роут `/admin` — часть общего Angular-бандла (не отдельная сборка): `outputPath` уже указывает
в `FamilyHub.Api/wwwroot`, разделение по факту достигается периметром и собственным гардом
(`adminGuard` → `GET /api/admin/session`), а не отдельным JS-бандлом.

## Последствия

- Ключи по-прежнему только в env, никогда в БД — ADR-0002 §4 не пересмотрен, только дополнен
  связкой вместо одиночного значения.
- Ротация Encryption — двухэтапная процедура (положить новый ключ в конфигурацию → редеплой →
  дождаться/запустить перешифровку → убрать отставной ключ из конфигурации), не мгновенная.
  Jwt/Attachments — быстрее (минуты, ограничено TTL токена/ссылки), фоновой джобы не требуют.
- Новая таблица `public."EncryptionRotationRuns"` — не персональные данные, ретеншн не задан
  (историю прогонов не чистим; при необходимости — отдельная задача).
- `docs/security/module-review-2026-08-02/00-INDEX.md`: пункт про ротацию ключей шифрования
  переведён из «Отложено намеренно» в закрытые. Пункт про удаление `X-Dev-TelegramId`
  по-прежнему открыт — эта работа его не затрагивала.
