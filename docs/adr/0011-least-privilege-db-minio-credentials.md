# ADR-0011. Отдельные учётки приложения для Postgres и MinIO

**Статус:** принят. **Дата:** 2026-09-24. Дополняет ADR-0009 (ротация ключей приложения): тот
закрыл ключи шифрования/подписи, этот — пароли к самим хранилищам.

## Контекст

Приложение ходило в Postgres под **суперпользователем** (`POSTGRES_USER` — тот, что создаёт
initdb) и в MinIO под **root** (`MINIO_ROOT_USER`). Одни и те же учётки использовали ещё бэкап и
DBeaver/`psql` по WireGuard. Следствия:

- Компрометация процесса приложения (утёкший дамп окружения, RCE) давала полный доступ ко всей
  БД (включая `pg_authid`, `COPY ... PROGRAM`) и ко всему MinIO, а не только к данным приложения.
- Сменить любой из двух паролей без простоя было невозможно: приложение читает строку подключения
  и креды MinIO один раз при старте (`IMinioClient` — синглтон), а единственный пароль нельзя
  «перекинуть» на новый, не оборвав работающий процесс.
- Контейнер `api` получал в окружении (`env_file: .env`) ВСЕ секреты стека, в том числе пароли
  суперпользователя и root, хотя для работы они ему не нужны.

## Решение

### 1. Postgres: роль-владелец и две логин-роли

- `familyhub_owner` (NOLOGIN) — владелец всех схем и объектов приложения (`identity`, `medical`,
  `kb`, `audit`, `hangfire`, `public`). Именно он «создаёт» таблицы: у логин-ролей задано
  `ALTER ROLE ... SET role = 'familyhub_owner'`, поэтому и EF-миграции, и установочные скрипты
  Hangfire порождают объекты, принадлежащие владельцу, а не тому, кто вошёл. Кто вошёл на самом
  деле, видно по `session_user`; `current_user` всегда `familyhub_owner`.
- `familyhub_app_a` и `familyhub_app_b` — две LOGIN-роли, обе члены владельца
  (`GRANT ... WITH INHERIT TRUE, SET TRUE`). Две, а не одна, чтобы ротация была без простоя:
  работает A → выдаём новый пароль B → переключаем приложение на B → отзываем A (и обратно).
- Суперпользователь остаётся для бэкапов (`pg_dump`) и ручной работы, но приложению его пароль
  больше не выдаётся.

### 2. Функции ротации вместо прав на роли

Приложению нельзя дать ни `CREATEROLE` (позволил бы создавать и менять ЛЮБЫЕ роли), ни
`ADMIN OPTION` друг на друга (круговое членство ролей в Postgres запрещено). Вместо этого —
схема `familyhub_admin` с тремя `SECURITY DEFINER`-функциями, владелец которых — суперпользователь:

| Функция | Что делает |
|---|---|
| `set_app_role_password(target, scram_verifier)` | ставит пароль и включает вход соседней роли |
| `disable_app_role(target)` | `NOLOGIN`, обнуляет пароль, **обрывает открытые сессии**, возвращает их число |
| `app_role_status()` | можно ли войти, есть ли пароль, сколько сессий — для админ-панели |

Все три работают только с `familyhub_app_a/b`, отказывают для любой другой роли (`42501`) и не дают
отключить роль, под которой работает вызывающий (`55006`). Пароль принимается только как **готовый
SCRAM-SHA-256-верификатор** (`22023` на открытый текст): открытый пароль иначе попал бы в лог
сервера при любой ошибке запроса. EXECUTE выдан только `familyhub_owner`, у `PUBLIC` его нет.

Обрыв сессий при отзыве — не косметика: Npgsql отдаёт соединение из пула **без повторной проверки
пароля**, поэтому без него приложение, ещё державшее старые соединения, продолжало бы работать под
уже «отозванной» ролью сколь угодно долго (это проверяется автотестом).

### 3. MinIO: service account пользователя с доступом к одному бакету

- Пользователь `familyhub-app` с политикой только на бакет приложения: чтение/запись/удаление
  объектов, листинг, multipart. Ни административных действий, ни создания бакетов. Бакет
  создаёт скрипт первичной настройки.
- Приложение работает под **service account** этого пользователя (access key + secret), а не под
  его логином. Ротация — выпуск нового service account рядом со старым (оба действуют одновременно,
  что и нужно для двухфазного переключения) и удаление старого.
- Проверено на реальном MinIO: service account без административных прав может создавать и
  удалять service account-ы **того же родителя**; выпущенный им ключ работает с бакетом, после
  удаления — перестаёт. Приложение при этом видит в `ListBuckets` только свой бакет.

### 4. Что остаётся у человека

Пароль суперпользователя Postgres и root MinIO ротирует оператор скриптами
`rotate-postgres-superuser.sh` / `rotate-minio-root.sh`. Приложение под ними не работает, поэтому
их смена **не затрагивает приложение** и не требует простоя (нужно обновить `PROD_ENV`, чтобы
контейнер `backup` и DBeaver получили новое значение).

### 5. Контейнер `api` не видит секреты суперпользователя

В `docker-compose.prod.yml` для `api` строка подключения и креды MinIO собираются из
`DB_APP_*`/`MINIO_APP_*` (обязательные, `${VAR:?}` — деплой без них падает с понятным сообщением,
а не стартует с пустыми кредами), а `POSTGRES_*`/`MINIO_ROOT_*` из `env_file` **перекрыты пустыми
значениями**.

## Последствия

- Утечка окружения приложения больше не отдаёт суперпользователя Postgres и root MinIO; доступ —
  только к схеме приложения и бакету приложения.
- Первичная настройка — один раз и **до** деплоя версии, требующей новые переменные (иначе
  `docker compose` отказывается стартовать `api`): `deploy/scripts/bootstrap-app-credentials.sh`,
  порядок действий — в `deploy/README.md`, «Учётки приложения». Скрипт идемпотентен по SQL;
  повторный запуск (`--force`) выпускает новые пароль БД и ключ MinIO, старый ключ MinIO остаётся
  действующим, пока его не отозвать.
- Ownership меняется у **существующих** объектов: передача владения берёт кратковременную
  блокировку каждой таблицы — выполнять в малонагруженное время. Суперпользователь при этом
  продолжает видеть и менять всё, так что откат на старые креды не требует обратной передачи.
- Дамп `pg_dump` содержит `OWNER TO familyhub_owner`: восстановление в **новый** кластер требует
  сначала создать роли (`bootstrap-roles.sql` без пароля) либо `pg_restore --no-owner
  --role=familyhub_owner`. Порядок описан в `deploy/README.md` §9.
- `deploy.yml` копирует `deploy/scripts/` на VPS, но сам скрипты не запускает — первичная настройка
  и ротации выполняются человеком осознанно.
- Dev-стек работает без настройки: в `docker-compose.yml` при незаданных `DB_APP_*`/`MINIO_APP_*`
  приложение по-прежнему ходит под `POSTGRES_USER`/`MINIO_ROOT_*`. Чтобы воспроизвести прод —
  `bash deploy/scripts/bootstrap-app-credentials.sh --dev`.

## Рассмотрено и отвергнуто

- **Одна роль приложения + смена её пароля.** Мгновенно ломает вход у работающего процесса (пул
  соединений, синглтон `IMinioClient`).
- **`CREATEROLE`/`ADMIN OPTION` у ролей приложения.** Первое даёт управление любыми ролями, второе
  невозможно из-за запрета кругового членства (A ↔ B).
- **Две статические учётки MinIO со сменой пароля через admin API.** Требует права
  `admin:CreateUser`, то есть возможность создавать и менять ЛЮБЫХ пользователей; старый секрет
  умирает сразу, двухфазного переключения нет.
- **`mc` внутри образа `api` и вызов подпроцессом.** Добавляет бинарник и запуск процессов в
  веб-приложение; для ротации service account-ов хватает подписанных запросов к admin API.

## Что сознательно не сделано

- Контейнер `caddy` по-прежнему получает весь `.env` (`env_file: .env`), в том числе пароли
  суперпользователя и root: ему нужны только переменные для `Caddyfile`. Сужение — отдельная задача.
- Образ MinIO в `docker-compose.prod.yml` остаётся `:latest` — закрепление версии привязано к
  реализации ротации из приложения (поведение admin API должно совпадать с версией в тестах) и
  делается вместе с ней. *(Позже закреплено в ADR-0012: образ собирается из исходников и лежит в
  нашем GHCR под явным тегом.)*
- Ротация из админ-панели («Безопасность → Учётки БД/MinIO») — следующий этап; эта работа готовит
  почву (роли, функции, service account), но приложение пока сами функции не вызывает.
