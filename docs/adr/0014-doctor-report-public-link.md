# ADR-0014. Отчёт для врача: PDF-снимок и публичная ссылка с токеном в БД

**Статус:** принят. **Дата:** 2026-09-26. Уточняет правило «файлы отдаются только по короткоживущим
подписанным ссылкам, выданным после проверки доступа» ([ADR-0002](0002-field-and-file-encryption-key-management.md),
[ADR-0009](0009-admin-panel-and-key-rotation.md) — `PreviousSigningKeys`) и использует сайдкар из
[ADR-0010](0010-attachment-previews-and-gotenberg.md).

## Контекст

Пациенту нужно отдать врачу сводку своих данных за период: динамику анализов, резюме, назначенные и
принятые препараты, домашние замеры и жалобы. Врач — человек без аккаунта в приложении и, как правило,
без мессенджера, в котором сидит пациент; у него есть браузер и 10–15 минут на приём.

Существующие ссылки на файлы (`DownloadTokenService`) для этого не подходят: они **stateless**, живут
5 минут (`Attachments:UrlTtl`), их нельзя ни отозвать, ни продлить, а доступ к ним выдаётся только
аутентифицированному пользователю, у которого есть право на запись-родителя. Врача в эту модель не
вписать, а держать открытой вечную ссылку без возможности отзыва — недопустимо для медданных.

## Решение

### 1. Отчёт — снимок, а не живой запрос
Отчёт строится **один раз** при создании (`DoctorReportService.CreateAsync`) и хранится как PDF.
Врач видит ровно то, что пациент собрал и отправил: последующие правки анализов, дневника или профиля
отчёт не меняют (публичная страница показывает снимок пациента — `PatientSnapshotJson`, а не текущий
профиль).

- **Пациент — только сам пользователь.** Записи, где он владелец и адресат, плюс записи, которые
  другие загрузили лично для него (`TargetUserId`). Подопечные, записи «за другого» и шаринг семьёй на
  отчёт не влияют. Дневник строго личный.
- **Блоки** включаются галочками: динамика анализов, ИИ-резюме, препараты, приёмы врача, домашние
  замеры/самочувствие/сон, симптомы и заметки. Заметки дневника с пометкой «в вопросы к врачу»
  попадают в блок жалоб всегда.
- **Препараты** — назначения из заключений визитов (`PrescribedMedications`) плюс приёмы из дневника
  (свободный текст). Аптечка не используется: она семейная и не привязана к человеку.
- **ИИ-резюме — только уже готовые** (`SummaryJson`), без нового вызова LLM; устаревшие (`SummaryDirtyAt`)
  пропускаются, и отчёт честно пишет, сколько пропущено. Новый LLM-вызов в синхронном запросе
  противоречил бы [ADR-0013](0013-llm-unavailability-waiting-queue.md).
- **PDF** — HTML→PDF через существующий Gotenberg (Chromium-маршрут), новых зависимостей и лицензий нет.
  Сайдкар недоступен → `503`, ничего не сохраняется (fail-soft, как у превью, но здесь без деградации:
  отчёт без PDF бессмыслен). Генерация синхронная — она секундная и не обращается к ИИ.

### 2. Хранение
PDF лежит в MinIO как обычный шифрованный блоб под строкой `FileAttachment` с
`OwnerType = DoctorReport` — так шифрование `IFileCipher`, ротация ключей ([ADR-0009](0009-admin-panel-and-key-rotation.md))
и удаление аккаунта работают без нового кода. Видимости через `AttachmentService` у такого вложения нет
(`HasAccessAsync` → `false` по умолчанию): подписанные ссылки на него выдать нельзя, доступ только
через `DoctorReportService`. Поля отчёта (`Recipient`, `PatientComment`, `ShareToken`, снимок пациента)
— `[Encrypted]`, сущность добавлена в `EncryptionRotationJob.FieldEntityTypes`.

### 3. Публичная ссылка — осознанное исключение
Ссылка `{origin}/r/{token}` → анонимные `GET /api/public/doctor-reports/{token}` и `/{token}/pdf`.

| Свойство | Решение |
|---|---|
| Токен | 32 случайных байта, base64url (256 бит); в БД — **SHA-256 хеш** (`ShareTokenHash`, unique) для поиска и зашифрованная копия (`ShareToken`), чтобы владелец мог скопировать ссылку повторно |
| Срок | 7 / 14 / 30 дней (14 по умолчанию), не больше 30; «Без ссылки» — только PDF |
| Управление | продлить (тот же токен, новый срок), выпустить новую (старый токен мёртв), отозвать (хеш и токен стираются) |
| Отказ | неизвестный, истёкший и отозванный токен — **один и тот же 404**; страница не раскрывает ни имени, ни периода |
| Аудит | каждое открытие PDF: `DoctorReportViewed` (актор `Guid.Empty` — смотрящий анонимен, владелец в `OwnerUserId`), счётчик и время у отчёта; выдача, продление и отзыв — `DoctorReportLinkIssued/Revoked` |
| Периметр | вне `ConsentRequiredFilter` (согласие дал пациент, выдав ссылку); лимит `public-report` — 30 запросов в минуту на IP; `noindex`, `Referrer-Policy: no-referrer` на странице; `Cache-Control: no-store` глобально на `/api/*` |
| Лимиты | период ≤ 2 лет, не больше 30 отчётов на пользователя |

Токен стоит в пути, а не в query: страница не отправляет его на сторонние хосты, а prefetch-боты
мессенджеров (Telegram и т. п.) ходят за HTML SPA, а не за API — счётчик открытий они не накручивают.

### 4. Жизненный цикл
- Удаление отчёта — строка, вложение и блоб; ссылка перестаёт работать сразу.
- Удаление аккаунта — отчёты, вложения и блобы удаляются (`AccountService`); в экспорт попадают
  метаданные отчётов (`doctor-reports.json`) **без токенов**, PDF не экспортируются (производный
  снимок данных, уже присутствующих в экспорте).

## Последствия

- Появляется единственный публично доступный без подписи-по-запросу медицинский документ. Смягчение —
  токен 256 бит, срок ≤ 30 дней, отзыв, аудит, rate limit, снимок только выбранных пациентом блоков.
  Пациент видит статус ссылки и счётчик открытий в списке отчётов («у кого открыты мои данные»).
- Часовой пояс пользователя серверу неизвестен: границы периода для дневника считаются по UTC.
- Отчёт не пересобирается: чтобы обновить данные, создаётся новый. Список отчётов ограничен 30 шт.
- Если понадобится доступ врача с подтверждением (одноразовый код и т. п.) — это отдельное решение
  поверх, токен-в-БД к нему готов.
