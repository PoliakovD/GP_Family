# ADR-0015. Напоминания о приёме лекарств: обобщённый push с кнопками и одноразовый токен действия

**Статус:** принят. **Дата:** 2026-09-26. Уточняет п. 2 [ADR-0004](0004-web-push-egress-exception.md)
(payload push всегда фиксированный), опирается на [ADR-0002](0002-field-and-file-encryption-key-management.md)
(что шифруется) и повторяет приём токена-хеша из [ADR-0014](0014-doctor-report-public-link.md).

## Контекст

Курс приёма лекарств (`MedicationCourse`) напоминает о каждом приёме, а «Принял / Отложить / Пропустить»
удобнее нажимать прямо в уведомлении, не открывая приложение. Это упирается в три ограничения:

- **ADR-0004:** push уходит через сторонние релеи (FCM/Mozilla/Apple), поэтому его текст всегда
  «FamilyHub / Новое уведомление» и ведёт на `/notifications`. Название препарата в нём — медданные.
- **Таблица `identity.Notifications` не шифруется**, а Telegram-канал пересылает `Title`/`Body` дословно.
  Значит, название препарата нельзя класть и в текст уведомления, не только в push-payload.
- **Кнопку выполняет service worker без сессии.** Cookie/JWT там нет, а Telegram-режим вообще
  аутентифицируется заголовком.

## Решение

### 1. Текст уведомлений — без препаратов и без лишних имён
- Напоминание: «Время принять лекарство» / «Напоминание о приёме в 14:00». Для курса подопечного
  в теле добавляется его имя («Бабушка: …»). Пропуск: «Пропущен приём лекарства» / «{Имя}: приём в 9:00 не
  отмечен». Запас: «Лекарство заканчивается» / «Проверьте аптечку».
- В push текст ещё строже: «FamilyHub» / «Время принять лекарство · 14:00» — без имён вовсе.
- Подробности (какой препарат, чей курс) — в приложении по `RelatedEntityId` (приём или курс).

### 2. Push может нести кнопки, тег и «тихий» режим (расширение ADR-0004 п. 2)
`WebPushNotificationSender` получает `IPushPayloadCustomizer`: тип уведомления добавляет к обобщённому
payload `tag`, `renotify`, `requireInteraction`, `silent`, `actions` и карту `data.onActionClick`.
Кастомизатор может вернуть `null` — «уведомление уже неактуально» (приём отмечен), push не шлётся.
Остальные типы остаются прежними — обобщённый текст и переход на `/notifications`.
Клик по самому уведомлению ведёт на `/health/intake/dose/{id}`, где приём подсвечен.

### 3. Кнопки — публичный эндпоинт с одноразовым токеном
- Angular ngsw уже умеет операцию `sendRequest`: `fetch(url)` в фоне (только GET, окно не открывается).
  Свой service worker для production не нужен; в dev-сборке (`push-sw.js`) то же сделано вручную.
- Токен: 256 случайных бит, привязан к одному приёму и получателю напоминания. В БД — только SHA-256
  (`DoseActionToken.TokenHash`); сам токен лежит только в push-payload, зашифрованном end-to-end
  (RFC 8291), — релей его не видит. Срок — до конца срока приёма плюс сутки, чистится часовой задачей.
- `GET /api/public/dose-actions/{token}?a=taken|snooze10|snooze30|skip` — анонимно, вне
  `ConsentRequiredFilter`, лимит по IP, `Cache-Control: no-store`. Неверный/просроченный токен и потерянные
  права получателя — один и тот же 404; повтор того же действия идемпотентен (204), другое действие по
  использованному токену или уже закрытый приём — 409.
- Действие выполняется от имени получателя с теми же проверками доступа, что и в приложении
  (`DoseService`): «Принял» списывает таблетку из аптечки и пишет в дневник (для своего курса) — ровно как
  кнопка в интерфейсе. «Пропустить» — осознанный отказ, семье о нём не сообщается.
- GET с побочным эффектом — осознанно: `sendRequest` иного не умеет, ссылка нигде не показывается,
  ответ не кешируется, повтор безопасен.

### 4. Ограничения, которые принимаем
- Chrome/Android показывают не больше **двух** кнопок (порядок: «Принял», «Отложить на 10 минут»), iOS —
  ни одной; все четыре — на экране приёма, куда ведёт клик по уведомлению.
- Telegram получает тот же обобщённый текст; inline-кнопок и тихих часов в нём пока нет (в
  `TelegramMessageRequestedEvent` нет полей кнопок/беззвучности).
- Часовой пояс пользователя хранится (`User.TimeZoneId`, приходит из браузера); времена расписания —
  «настенные» в этом поясе, тихие часы (`QuietHoursFrom/To`) — пользовательские.

### 5. Модель данных и доступ
- Курс — для самого пользователя **или** подопечного. Взрослый с аккаунтом ведёт свой курс сам, а его
  близкие — наблюдатели (`MedicationWatcher`): читают курс и получают уведомления о пропусках, пока
  остаются в общей активной семье; за подопечного действует любой член его семьи.
- Будущие приёмы не хранятся: расписание разворачивается на лету (`DoseScheduleExpander`), строка
  `MedicationDose` появляется, когда приём наступил (минутная задача) или его отметили. Правка расписания
  меняет только будущее (`EffectiveFromUtc`).
- В дневник пишутся только собственные курсы (дневник строго личный); остаток списывается из семейной
  аптечки через compare-and-swap по `Medication.DataJson`.

## Последствия

- Уведомления о приёмах не раскрывают препараты ни релею push, ни Telegram, ни таблице уведомлений.
- Появляется анонимная точка входа с побочным эффектом; её защищают токен (256 бит, хеш, одноразовость по
  действию, срок), лимит по IP и проверка прав получателя в момент действия.
- Часовая и минутная фоновые задачи (`medication-course-maintenance`, `medication-dose-scan`) — новая
  постоянная нагрузка на Hangfire; обе идемпотентны (`DedupKey`, уникальный индекс приёма).
