# ADR-0002. At-rest шифрование и управление ключами

**Статус:** принят (этап 2, задача 2.2). **Дата:** 2026-07-22.

## Контекст

Медданные должны храниться обезличенно и зашифрованно (152-ФЗ); ключи — вне БД.
Схемы БД разделены: `identity` (ПДн), `medical` (обезличенное, привязка только к
UUID пользователя), `kb` (обезличенный справочник), `audit` (журнал доступа), `public`
(инфраструктурное: outbox, миграции; Hangfire — своя схема `hangfire`).

## Решение

1. **Алгоритм:** AES-256-GCM (аутентифицированное шифрование: подмена шифротекста
   детектируется тегом, а не читается как мусор).
2. **Поля** (`[Encrypted]` + EF ValueConverter, формат `enc:{keyId}:{base64(nonce||tag||ct)}`):
   `MedicalRecord.PersonName/Doctor/Description/ExtractedDataJson`, `Birthday.PersonName`,
   `FileAttachment.FileName`. Ключи хранилища вложений не содержат имён файлов.
   `MedicalRecord.ExtractedDataJson` — заготовка под OCR-конвейер (задачи 5.2/5.3, ещё не
   реализован); зашифрован тем же способом, что и остальные поля записи.
3. **Файлы** (`IFileCipher`, формат `FHE1 + keyId + nonce + tag + ct`): блоб шифруется
   целиком до записи в MinIO (единственная реализация `IFileStorage` — `LocalFileStorage`
   упразднён, в т.ч. в Development: см. «Обезличенные ключи объектов» ниже); скачивание —
   только через API-эндпоинт с расшифровкой по короткоживущей HMAC-ссылке (presigned-URL
   хранилища упразднены — они отдавали бы шифротекст).
7. **Обезличенные ключи объектов:** ключ объекта в MinIO не несёт никакой семантики —
   ни типа записи, ни владельца, ни группировки сканов по одной медкарте
   (`StorageKeyFactory`, `Infrastructure/Storage/`): `blobs/{a}/{b}/{attachmentId}`, где
   `{a}{b}` — первые байты `attachmentId` (двухуровневый шард, чтобы листинг бакета не
   деградировал). Раньше ключ был `medical-records/{recordId}/{attachmentId}` — администратор
   хранилища видел, что несколько объектов относятся к одной записи (то есть к одному
   человеку), даже не имея доступа к шифротексту. Связь blob ↔ запись живёт только в
   `medical."FileAttachments"."StorageKey"`.
4. **Ключи вне БД:** мастер-ключ — env `Encryption__MasterKey` (base64, 32 байта),
   задаётся секретом деплоя (prod.env), в БД и бэкапы БД не попадает.
   Потеря ключа = потеря данных: ключ бэкапится отдельно от БД (менеджер секретов).
5. **Ротация:** префикс `keyId` (`ActiveKeyId`, сейчас `v1`) зашит в каждое значение.
   Процедура: добавить новый ключ → фоновая перешифровка (чтение старым, запись новым)
   → удалить старый. Реализовано в ADR-0009 (`IEncryptionKeyRing`, `EncryptionRotationJob`,
   вкладка «Ключи» админ-панели) — см. его для деталей связки ключей и двух фаз перешифровки.
6. **TLS in-transit:** внешний трафик терминируется reverse-proxy с TLS; подключение
   к Postgres в проде — `Ssl Mode=Require` в строке подключения.

## Что сознательно НЕ шифруется (остаточные риски)

| Данные | Причина |
|--------|---------|
| `Birthday.Date` | SQL-фильтр ежедневной джобы напоминаний; дата без имени (оно зашифровано) — низкий риск |
| `Notification.Title/Body` | назначение данных — отправка в Telegram открытым текстом; содержит максимум имена; ретеншн прочитанных — кандидат этапа 3 |
| `Medication.*` | сведения о препарате семейной аптечки, не о человеке |
| `OutboxMessages.Payload` | снимки событий (могут содержать имена); митигация — авточистка обработанных строк через 7 дней (`OutboxOptions.ProcessedRetention`) |

## Последствия

- Шифрованные поля нельзя фильтровать/искать на стороне SQL (сейчас таких запросов нет;
  полнотекстовый поиск этапа 3 должен строиться на app-level индексации).
- `AppDbContext` требует `IFieldCipher`-синглтон (EF кэширует модель с конвертером).
- Юнит-тесты работают на SQLite: провайдер игнорирует схемы, шифрование — app-level.
