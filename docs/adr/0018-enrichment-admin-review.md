# ADR-0018. Ручное одобрение платных поисков и результатов обогащения

**Статус:** принят. **Дата:** 2026-10-01. Расширяет [ADR-0005](0005-medication-enrichment-egress.md) п. 9
(вентиль платного поиска): вентиль остаётся глобальным «стоп-краном», но больше не единственный контроль —
каждый платный поиск теперь ждёт решения человека.

## Контекст

Обогащение справочников препаратов (`kb.global_medications_kb`) и лабораторных показателей
(`kb.global_lab_analytes_kb`) работало полностью автоматически: сохранили название — задача сама сходила в
платный поиск (Yandex/Brave, ~5 ₽ за вызов), локальная модель сделала краткое изложение, и оно сразу легло в
справочник, который читают все пользователи. Из контроля были только вентиль (`WebSearchConfig.IsPaused`,
задачи уходят в `Deferred`) и антигаллюцинационный гейт (`usedSourceIndexes`). Не было ни способа остановить
сомнительный платный запрос (искажённое OCR-имя, странный вручную введённый показатель), ни способа не пустить в
справочник ответ, в котором сама модель не уверена. А правка уже записанного шла через каталог админки
(`AdminCatalogService`) — отдельным длинным путём.

## Решение

### 1. Два гейта, два новых статуса задачи

`EnrichmentJobStatus`: `AwaitingSearchApproval = 6`, `AwaitingResultReview = 7`. Оба **живые** (не терминальные) и
входят в частичный уникальный индекс дедупа `Status IN (0,1,5,6,7)` во всех трёх таблицах задач
(`MedicationEnrichmentJobs`, `VisitMedicationEnrichmentJobs`, `LabAnalyteEnrichmentJobs`) — без этого повторный
запрос того же названия создал бы дубль в очереди. Набор «живых» статусов вынесен в `EnrichmentJobStatusSets.Live`
(им же пользуются запросы дедупа, sweep, карточка аптечки), юнит-тест сверяет его с фильтром индекса.

- **Гейт 1 — платный поиск.** В трёх процессорах на том же месте, где раньше проверялся вентиль (только на
  кэш-промахе и только при реальном, не `Null`-провайдере): если у задачи нет `SearchApprovedAt`, она сохраняет
  `QueryConfidence`/`QueryConfidenceReason` и предложенный текст запроса `ProposedQueryText` (нормализованное имя),
  уходит в `AwaitingSearchApproval` и **возвращается без исключения** (как `Deferred`). **Кэш-хит бесплатен и
  проходит сразу** — одобрения не требует. Вентиль действует **поверх** одобрения: одобренная задача при закрытом
  вентиле уходит в `Deferred` (`SearchApprovedAt` сохранён — повторно не спросим).
- **Гейт 2 — результат.** После суммаризации, если `confidence` суммаризатора ниже порога **или отсутствует**,
  `KbWriter`/`LabAnalyteKbWriter` не вызываются: черновик (`DraftPayloadJson` — разрешённое имя, алиасы, `Summary`,
  снимок использованных сниппетов, атрибуция полей) лежит в задаче, статус `AwaitingResultReview`.

### 2. Уверенность модели

Контракты JSON расширены полями `confidence` (0..1) и `confidenceReason`: у `LegitimacyGuardService` и
`AnalytePlausibilityGuardService` (этап запроса — страж перед платным поиском; для ручного ввода показателя берётся
минимум из двух стражей), у `MedicationSummarizer` и `LabAnalyteKbSummarizer` (этап результата). Разбор —
`LmStudioPayloadReader.ReadConfidence`: нет поля, не число или **значение вне [0..1]** → `null` (в границу не
подгоняется). **`null` всегда считается «ниже порога»** (`EnrichmentReviewThresholds.IsConfident`) — отсутствие
оценки не должно пропускать задачу без человека. Промпты живут в БД с версиями: миграция
`AddEnrichmentAdminReview` добавляет новые активные версии четырёх слотов (`guard.legitimacy-check`,
`analysis.analyte-plausibility`, `medication.summarize`, `lab-analyte.summarize`) как копию текущей активной +
дописанный блок с требованием полей (дописывание, а не замена якорной фразы — тела могли быть переписаны из админки);
код-фолбэки обновлены так же. Суммаризаторы дополнительно возвращают `fieldSources` — «поле → индексы сниппетов»
(см. п. 6).

Конвейер заключений врача (`VisitMedicationEnrichmentProcessor`) собственного шага легитимности не имел — на гейте 1
оценку снимает тот же `ILegitimacyGuardService`; отказ стража там **не останавливает задачу** (поведение конвейера
не меняем), а превращается в уверенность 0 с причиной — админ видит красную строку и решает сам.

### 3. Пороги

Singleton `EnrichmentReviewConfig` (нет строки = значения по умолчанию, как у `WebSearchConfig`): четыре порога —
`{препараты, показатели} × {запрос, результат}`; по умолчанию запрос 0.7, результат 0.8. `IEnrichmentReviewConfigService`
читает **без кеша**: правка действует на следующей же задаче. Значения вне 0..1 (и NaN) отвергаются
(`ArgumentOutOfRangeException` → HTTP 400). Админ-UI — «Настройки confidence» (слайдер + поле на каждый порог).

### 4. Очередь «Одобрение» (единый Inbox)

`/api/admin/review/*` (`AdminEnrichmentReviewEndpoints`, `AdminEnrichmentReviewService`). Единственный код, который
выводит задачу из статусов 6/7. Поиски и результаты — **один список**: «ниже порога» (в том числе без оценки) —
красным и первыми, внутри — FIFO. Список по трём видам задач (`lab-analyte`/`medication`/`visit-medication`),
отдельные `GET /searches`, `GET /results` оставлены.

- **Поиск:** `approve {queryText?, mode?, twinCacheId?, note?}`; `reject {reason, note}` → `Failed` +
  `EnrichmentFailureReason.RejectedByAdmin` (смысловой отказ человека: пользователя не уведомляем, в «Требует
  внимания» не показываем; повторный автозапрос того же имени блокирует обычная проверка `alreadyFailed`);
  пакетные `bulk-approve`/`bulk-reject` (≤100). Одобрение ставит `SearchApprovedAt`, `Pending`, обнуляет `Attempts`
  (попытка, потраченная на «парковку», не должна сокращать ретраи реального прогона) и энкьюит процессор в одной
  транзакции со строкой. Правка текста запроса проходит `KbIsolationGuard` — это egress во внешний сервис (ADR-0005).
- **Результат:** деталь (`GET /items/{kind}/{id}`): черновик в форме записи kb (тот же jsonb, что ляжет в
  справочник), текущая запись для сравнения, уверенность и причина, источники и атрибуция полей. `approve {payloadJson?,
  displayName?, aliases?}` — запись **существующими писателями** + (если админ что-то поправил) тем же путём, что ручная
  правка каталога (`AdminCatalogService.Update*`), поэтому **изменённые поля попадают в `LockedFields`**: лочатся только
  реально отличающиеся ключи верхнего уровня (`payload.<key>`), а не весь payload; всё — в одной транзакции со сменой
  статуса и публикацией `MedicationEnrichedEvent`. `reject`; `resummarize` — пересуммаризация без нового платного поиска.
- **Заметка админа** к решению (`ReviewNote`) — не уходит ни во внешний поиск, ни в модель.
- Счётчик очереди — в «Требует внимания» (`AdminAttentionDto.ReviewQueue`) и бейджем в меню админки.

**Что не обходит одобрение.** `DeferredEnrichmentReleaseJob` берёт только `Deferred`; `LmStudioRecoverySweepJob`
возобновляет только `Failed`+`IsTransientFailure` и теперь считает 6/7 «живыми» (иначе упёрся бы в уникальный индекс);
ручной retry из «Операции → Задачи» (`ResetAndEnqueueAsync`) для задач 6/7 возвращает **409** (иначе сброс в `Pending`
стёр бы ожидающий черновик). Даже если бы задачу всё же перезапустили, гейт стоит в самом процессоре и проверяет
`SearchApprovedAt`. Прогрев кэша (`SearchCacheWarmupJob`) одобрения не требует: его запускает сам админ, платный бюджет
задан явно (ADR-0005 п. 9).

### 5. Источники и ручное наполнение кэша

Набор сниппетов строки кэша поиска правится из карточки задачи; каждая правка пишется в журнал (п. 7).
`WebSnippet` получил `Origin` (`Auto`/`Manual`), `Kind`, `Note`, `Pinned`; старые строки читаются как `Auto`.

- Ручные сниппеты: `manual-quote` (ссылка + короткая цитата) и `expert-knowledge` (знание эксперта без URL —
  служебный `expert://admin/<id>`, подпись источника «Эксперт: админ»). **Лимит текста 800 символов** — код
  принимает короткую выдержку, не статью целиком. Недоверенный домен — **предупреждение, не блокировка**.
- Ручные сниппеты и закреплённые **не перезаписываются** автообновлением кэша (`SearchCacheSnippets.MergeAfterSearch`)
  и чисткой строк с неразрешённым биоматериалом; старый редактор кэша («замена списка») не стирает их
  (`MergeAfterReplace`). Удалить ручной сниппет можно только явно.
- `EnrichmentSnippetFilter.SelectForSummary`: включённые сниппеты, ручные и закреплённые — первыми и **не отсекаются**
  `MaxSnippets`; явный override админа по-прежнему побеждает. Закрепление включает сниппет (`override=true`).
- «Пересуммировать» берёт набор из **текущего состояния кэша** (после правок админа), тот же отбор, что у процессора.
- Режим одобрения поиска **«использовать кэш»** (`mode=use-cache`): делает строку кэша свежей, процессор берёт набор из
  неё и в платный поиск не идёт (нужен хотя бы один включённый сниппет).
- **«Взять из готового кэша»** (дополнение): задача паркуется только на промахе кэша по *точному* имени, поэтому
  «мой набор» и «двойник» на практике почти не встречались — оставался платный поиск или ручной набор сниппетов.
  Теперь админ ищет по **любым непустым строкам кэша той же темы** (`GET /api/admin/review/items/{kind}/{id}/cache-candidates`,
  подстрока `NormalizedName` в сыром виде и после нормализатора темы; без запроса — по словам имени задачи; своя
  строка исключена), отмечает нужные сниппеты и импортирует их (`POST …/cache/import`,
  `SearchCacheEditor.ImportFromAsync`: без дублей по URL, свои сниппеты и override'ы не перетираются, свежесть строки
  не трогается — её ставит «использовать кэш»). Журнал: `cache-import`.
- **Правка сниппета** (`PUT /api/admin/review/cache/{topic}/{cacheId}/snippets`, `SearchCacheSnippets.ApplyEdit`):
  заголовок, текст, заметка. Текст не длиннее `max(800, исходная длина)` — выдержку можно подрезать/поправить, но не
  превратить в статью. Правленый авто-сниппет становится ручной цитатой (`Manual` + `manual-quote`) и поэтому
  переживает автообновление кэша. Журнал: `cache-edit`.

### 6. Атрибуция полей

Суммаризаторы возвращают `fieldSources` (`{"purpose":[0,2],…}`); для `refRanges` источник — `sourceIndex` самих
диапазонов. Карточка показывает «откуда поле» и **подсвечивает жёлтым непустые поля без источника**. Если модель
атрибуцию не вернула вообще (старая версия промпта), подсвечивать нечего — иначе жёлтым было бы всё.

### 7. Журнал изменений с откатом

`kb.change_log` (`KbChangeLog`): кто (`admin`/`system` — админ платформы единая учётка без строки `User`), когда,
снимки «было/стало» (JSON), действие, заметка. Пишут писатели kb (автообогащение, `ai-write`), каталог админки
(`admin-edit`/`admin-delete`/`admin-merge`/`verify`), правки набора сниппетов (`cache-*`), сам откат (`revert`).
Запись журнала — raw SQL (`KbChangeLogService`), чтобы не флашить чужие изменения общего `DbContext` посреди транзакции
процессора. **Откат одной версии** (`POST /api/admin/history/{id}/revert`): создание откатывается удалением, удаление —
восстановлением, изменение — возвратом к снимку «было»; откат — тоже запись журнала; одну запись откатываем один раз,
«откат отката» запрещён (нужную версию выбирают в истории); коллизия ключа при восстановлении → 409.

### 8. Статус проверки записи kb (внутренний маркер админа)

`VerificationStatus ∈ {AiUnverified, AdminVerified, AdminEdited, ManualKnowledge}`, `VerifiedAt`, `VerifiedPayloadHash`
(SHA-256 канонического payload: порядок ключей не важен). Одобрение без правок → `AdminVerified` (либо
`ManualKnowledge`, если черновик опирается только на знание эксперта); одобрение/правка с изменениями →
`AdminEdited`; «Отметить проверенным» без правок — отдельная кнопка. **Автообогащение, изменившее payload, сбрасывает
статус в `AiUnverified`** (совпавший payload — не сбрасывает; залоченный payload автообогащение не трогает вовсе).
Пересборка справочника показателей (`LabAnalyteKbRebuildJob`) не удаляет проверенные строки так же, как залоченные.
**Поля «кто проверил» (`VerifiedByUserId`) нет** сознательно: схема `kb` не хранит персональный контекст
(`KbIsolationGuardTests` отвергает `UserId` в любой kb-таблице), а админ платформы — не пользователь; «кто/когда» ведёт
журнал. Статус **не отдаётся пользовательским API/DTO и не показывается в пользовательском фронте** — только в
админских эндпоинтах и админ-UI (бейдж, фильтр «непроверенные», счётчик «проверено X из Y»); это охраняют
`KbVerificationNotExposedTests` (рефлексия по DTO) и интеграционный тест на реальных ответах `/api/kb/*`.

### 9. Группы поиска биоматериалов (дедупликация платного поиска)

Ключ кэша `LabAnalyteSearchCache` был `(название, биоматериал)`, а поисковый запрос подставляет биоматериал в текст —
АЧТВ × (кровь, венозная кровь, плазма) стоил три платных поиска. Теперь у `GlobalSpecimenKb` есть `SearchGroupKey`
(nullable; null = биоматериал сам по себе), а ключ кэша — `(название, SearchGroupKey)`: `"group:кровь"` либо
`"specimen:<id>"` (прежнее поведение). Слово группы подставляется в запрос вместо названия биоматериала. **Запись в kb
остаётся отдельной на каждый биоматериал** (нормы различаются, напр. глюкоза венозная/капиллярная). Автоматически
схлопываются только биоматериалы **одной** группы; между разными группами — только подсказка.
Миграция `AddSpecimenSearchGroups` задаёт стартовую группу «кровь» (кровь, венозная кровь, плазма) и одноразово
схлопывает уже накопленные строки кэша внутри группы (остаётся самая свежая; override'ы проигравших в SQL не
переносятся — ручных сниппетов до этой миграции не существовало). Присвоение группы из админки
(`Справочник → Биоматериалы`, `SpecimenSearchGroupService`) сливает строки так же, но переносит ручные сниппеты и
override'ы проигравшей; выход из группы даёт биоматериалу копию кэша. В очереди для нового платного поиска показателя
видны **«двойники»** — свежий кэш того же названия у другой группы; действие по умолчанию — «использовать этот кэш»
(бесплатно), платный поиск — явный выбор «искать отдельно».

### 10. Пользователю — «на проверке»

В карточке препарата (`GET /api/medications/{id}/kb`) статусы 6/7 показываются новым значением `UnderReview`
(«информация на проверке у администратора»); в списках чипы «уточняем…» считают их живыми задачами. Прочие места, где
статус виден пользователю, трогать не потребовалось.

## Последствия

- Каждый платный поиск требует клика админа; очередь — новая операционная нагрузка. Для снижения: пороги настраиваются,
  кэш-хиты и «двойники» бесплатны, есть пакетные действия и горячие клавиши.
- Админ платформы — одна учётка: `ReviewedByUserId`/`UpdatedByUserId` остаются `null` (поля зарезервированы), аудит —
  `ReviewedAt`, заметка и журнал.
- Результат с низкой уверенностью живёт в `DraftPayloadJson` задачи (снимок сниппетов внутри черновика — чтобы индексы
  использованных источников не «поехали», когда кэш обновят).
- Миграции: `AddEnrichmentAdminReview` (схема + промпты), `AddEnrichmentReviewNote`, `AddKbVerificationAndChangeLog`,
  `AddSpecimenSearchGroups` (со слиянием).
