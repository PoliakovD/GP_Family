# ADR-0003. Архитектура поиска: Postgres FTS + in-memory, отказ от OpenSearch

**Статус:** принят (этап 3). **Дата:** 2026-07-23.

## Контекст

Этап 3 требует полнотекстовый поиск по медданным с русской морфологией (словоформы: «анализ» /
«анализы» / «анализов») и устойчивостью к опечаткам распознавания OCR («гемоглабин» →
«гемоглобин»), а также единый вход для гибридного доступа (Telegram Mini App + PWA).

Данные, по которым нужен поиск, неоднородны по модели хранения:
- `Medication.Name`/`DataJson` (`medical.Medications`) и весь `kb.global_medications_kb` —
  **плейнтекст**: сведения о препарате/справочник, не о человеке (ADR-0002).
- `MedicalRecord.PersonName/Doctor/Description` и `FileAttachment.FileName` —
  **зашифрованы at-rest** (AES-256-GCM, EF `ValueConverter`, ADR-0002 п.2): в колонках лежит
  `enc:{keyId}:base64(...)`, физически непригодно для SQL-стороннего полнотекстового индекса.
- ADR-0001 запрещает хранение и обработку медданных за пределами РФ-контура и требует локальной
  инфраструктуры без лишних внешних stateful-сервисов.

Действующие ограничения (ADR-0002, «Последствия»): «шифрованные поля нельзя фильтровать/искать
на стороне SQL... полнотекстовый поиск этапа 3 должен строиться на app-level индексации» —
для части данных это было предопределено заранее.

## Решение

1. **Гибридная модель поиска, без единого внешнего поискового движка.**
   - **Postgres full-text search** — для плейнтекст-данных (`Medication.*`,
     `kb.global_medications_kb`): генерируемая STORED-колонка
     `search_vector tsvector` (`to_tsvector('russian', ...)`, конфигурация `russian` —
     встроенный Snowball-стеммер) + **GIN**-индекс для скорости, плюс расширение **`pg_trgm`**
     (`similarity()`, GIN по `gin_trgm_ops`) — устойчивость к опечаткам OCR. Реализовано raw-SQL
     миграцией (`AddFullTextSearch`), т.к. `search_vector` не заведена в EF-модель — она не нужна
     приложению как сущность, только как индекс под запрос.
   - **In-memory поиск** — для зашифрованных медкарт: `MedicalRecordService.SearchAsync`
     переиспользует существующий инвариант видимости (`VisibleRecordsQuery` — владелец + активный
     шаринг, минус точечно скрытое), EF расшифровывает поля конвертером при материализации, дальше
     матчинг идёт в памяти процесса через компактный self-contained модуль
     (`RussianStemmer` + `TrigramSimilarity`, тот же алгоритм Snowball, что и Postgres-конфиг
     `russian`, — поведение совпадает по обоим путям). Объём безопасен: список ограничен scope
     одного пользователя/семьи (сотни-тысячи записей), не всей базой.
   - **`SearchService`** — фасад `/api/search`, объединяющий оба источника + справочник, с
     **независимым контролем доступа на каждый источник** (семьи пользователя — для лекарств,
     владелец/шаринг — для медкарт, без ограничений — для обезличенного справочника).
2. **Отказ от OpenSearch/Elasticsearch как отдельного поискового движка.** Причины:
   - **Нарушение ADR-0001.** Внешний поисковый кластер — ещё один stateful-сервис в РФ-контуре
     (доп. хостинг, доп. поверхность egress-политики) без функциональной необходимости.
   - **Конфликт с моделью шифрования ADR-0002.** Индексация в OpenSearch потребовала бы
     скопировать расшифрованные ПДн (имя, врач, описание) во внешний индекс — второе хранилище
     чувствительных данных вне пути шифрования БД, удвоение поверхности утечки и отдельная
     ретеншн/шифрование-политика для индекса.
   - **Избыточность для объёма задачи.** Поиск скоупится одной семьёй/пользователем — от сотен
     до тысяч записей; кластер полнотекстового поиска — эксплуатационная и лицензионная
     избыточность (отдельный процесс, JVM, мониторинг, бэкапы) там, где Postgres GIN-индекс и
     in-memory матчинг справляются с запасом.
   - Postgres уже является системой хранения (единственной БД проекта) — не вводим новую
     технологию туда, где встроенных возможностей провайдера достаточно.

## Последствия

- FTS-часть тестируется только на реальном Postgres (SQLite-юнит-тесты её не видят — миграция
  не исполняется при `EnsureCreated()`); интеграционные тесты (`SearchApiTests`) гоняются на
  Testcontainers-Postgres и проверяют и словоформы, и опечатки, и разделение доступа по каждому
  источнику отдельно.
- In-memory поиск по медкартам не масштабируется горизонтально за пределы одного инстанса без
  дополнительной работы — приемлемо согласно ограничению single-instance из ADR-0001
  (горизонтальное масштабирование уже требует отдельного пересмотра in-memory rate-limit-счётчиков).
- Два независимых движка морфологии (Postgres `russian` snowball и `RussianStemmer` в C#) должны
  синхронно повторять один и тот же алгоритм — при расхождении поведения поиск по лекарствам и
  поиск по медкартам будут находить слова по-разному. Риск ограничен: оба реализуют один и тот же
  публично специфицированный алгоритм (Snowball Russian stemmer).
- Появление специализированного полнотекстового движка (OpenSearch и т.п.) в будущем возможно
  только через пересмотр этого ADR — с явным ответом на пп. 1-3 «Решения» (РФ-размещение,
  модель шифрования, объём данных).
