# ADR-0004. Web Push: исключение из egress-политики ADR-0001

**Статус:** принят (редизайн навигации). **Дата:** 2026-07-24.

## Контекст

Оповещения (`Notification`, задача 3 п.10) доставляются пользователю через `INotificationSender` —
на сегодня единственная реальная реализация, `TelegramNotificationSender`, шлёт сообщение боту по
`User.TelegramId`. **PWA-пользователь без привязанного Telegram оповещений не получает вообще** —
у него есть только пассивный инбокс `GET /api/notifications`, который нужно открыть самому.

Стандарт Web Push устроен так, что доставка ВСЕГДА идёт через push-релей браузера — сервер
конкретного вендора, на который подписывается браузер при вызове `SwPush.requestSubscription()`:
`fcm.googleapis.com` (Chrome/Edge), `updates.push.services.mozilla.com` (Firefox),
`web.push.apple.com` (Safari). Это архитектурное свойство протокола, а не выбор реализации —
обойти push-релей нельзя, не переставая быть Web Push.

ADR-0001 задаёт egress-политику хоста как явный allowlist: «исходящий трафик API-контейнера
разрешён ТОЛЬКО к: PostgreSQL/MinIO/Seq/LM Studio (приватная сеть); `api.telegram.org`; SMTP-хосту
РФ-провайдера. Всё остальное — deny by default», и обязывает по чек-листу перед любым новым
исходящим вызовом отвечать на вопрос «сервис размещён в РФ? проходит ли через него ПДн?». Push-релеи
иностранные (США/Mozilla/Apple) — формально новая исходящая зависимость требует именно этого ADR.

## Решение

1. **Разрешить исходящий HTTPS к push-релеям браузеров** как дополнение к allowlist ADR-0001 п.3:
   `fcm.googleapis.com`, `*.googleapis.com` (FCM использует поддомены), `updates.push.services.mozilla.com`,
   `web.push.apple.com`. Egress-правило добавляется в инфраструктурный allowlist наравне с
   `api.telegram.org`.
2. **Через push-релей проходит ТОЛЬКО обобщённый, не персональный текст.** `WebPushNotificationSender`
   (`src/FamilyHub.Infrastructure/Notifications/WebPushNotificationSender.cs`) сознательно НЕ
   пересылает `Notification.Title`/`Body` (которые ADR-0002 уже отмечает как потенциально
   содержащие имена) — payload всегда фиксированный: `"FamilyHub" / "Новое уведомление"` + ссылка
   `/notifications`. Реальный контент пользователь видит только открыв приложение — через уже
   аутентифицированный (`authInterceptor`/cookie) `GET /api/notifications`, который push-релей
   никогда не видит.
3. **Payload шифруется по RFC8291** (VAPID + ECDH, реализация — пакет `WebPush`): даже обобщённый
   текст push-релей физически не может прочитать, шифрование end-to-end между API и браузером.
   Push-релей видит только метаданные доставки (endpoint, размер, тайминг) — не содержимое.
4. **Ключи и подписки — вне зоны риска ПДн.** VAPID-ключи — конфиг вне БД (`WebPush:*`, тот же
   принцип, что `Encryption:MasterKey`). Endpoint/P256dh/Auth конкретной подписки браузера хранятся
   `[Encrypted]` в `identity.PushSubscriptions` (ADR-0002-стандарт) — сами по себе они не ПДн о
   здоровье, но credential-подобны (позволяют слать push на конкретное устройство).
5. **Доставка — best-effort, независимый канал.** `NotificationSendingService.TrySendAsync` фан-аутит
   на ВСЕ зарегистрированные `INotificationSender` (Telegram и/или Web Push, оба могут быть
   настроены одновременно) — сбой одного канала не блокирует другой; протухшие (404/410) подписки
   удаляются автоматически.

## Последствия

- Обновлён чек-лист ADR-0001 п.3 (egress-allowlist) — добавлен пункт «push-релеи браузеров (см.
  ADR-0004)» как явное поименованное исключение, а не молчаливое расширение allowlist.
- Любой будущий push-провайдер (например, отдельный self-hosted push-relay) потребовал бы
  пересмотра уже этого ADR, а не повторной ревизии ADR-0001.
- Ограничение осталось: **содержимое push-уведомления в OS-трее всегда обобщённое** — сознательный
  компромисс UX (нет персонализации в самом уведомлении) в обмен на то, что push-релей физически не
  может утечь медицинские данные, даже будучи скомпрометированным.
- PWA-пользователи без Telegram теперь получают реальные push-уведомления — закрывает пробел,
  описанный в контексте.
