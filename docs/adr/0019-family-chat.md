# ADR-0019. Чат семьи: SignalR без бэкплейна, вход в хаб по тикету, события без содержимого

**Статус:** принят. **Дата:** 2026-10-13. Реализует п. 14 дорожной карты брифа («внутрисемейный чат»).
Уточняет [ADR-0004](0004-web-push-egress-exception.md) и [ADR-0015](0015-medication-dose-reminders-push-actions.md) для нового
типа уведомления.

## Контекст

В брифе чат заявлен как семейный ресурс: читают члены семьи, модерирует админ семьи, транспорт SignalR
(+ Redis-бэкплейн). Realtime-слоя в проекте до сих пор не было — всё на поллинге. Объём v1 согласован с владельцем:
**один общий чат на семью** (пользователь в нескольких семьях — несколько чатов), текст, фото/файлы, ответы,
реакции, ссылки на сущности приложения; доставка — SignalR в открытом приложении и push/Telegram, когда оно закрыто.

Ограничения, которые определили решение:

- две схемы входа: PWA — httpOnly-cookie с JWT, Mini App — заголовок `Authorization: tma <initData>` на
  **каждый** запрос. Браузерный WebSocket произвольных заголовков не шлёт;
- часть сущностей, на которые хочется сослаться в чате (мед-записи, курсы приёма), — **персональные** с
  индивидуальной видимостью (ADR-0017), а не семейные;
- текст уведомлений не шифруется и уходит в Telegram/push-релеи как есть: туда нельзя ни медданные, ни имена
  (ADR-0004, ADR-0015, политика конфиденциальности);
- API в проде — одна реплика.

## Решение

### 1. Модуль `FamilyHub.Modules.Chat`

Отдельный модуль по образцу Birthdays (`AddChatModule()`/`MapChatModule()`), зависит только от Domain и
Infrastructure. Сущности — в Domain (`ChatMessage`, `ChatMessageReaction`, `ChatMessageLink`, `ChatReadState`),
`ChatMessage.FamilyId` — FK с каскадом от семьи. Текст сообщения — `[Encrypted]` (ADR-0002): чат семьи на
практике будет про здоровье. Следствие — серверного поиска по чату нет.

### 2. SignalR без Redis-бэкплейна

`/hubs/chat`, in-memory. Бэкплейн (`AddStackExchangeRedis`) добавляется вместе со второй репликой API —
до тех пор Redis — лишний сервис на ВДС. Клиент при подключении автоматически попадает в группы
`family:{id}` всех своих активных семей.

### 3. Вход в хаб — короткоживущий тикет

`POST /api/chat/hub-ticket` проходит обычную аутентификацию (cookie+CSRF или `tma`) и согласие на обработку
ПДн, и выдаёт HMAC-тикет `userId:expires` со сроком **60 с**. Клиент отдаёт его через `accessTokenFactory`;
схема `HubTicket` принимает `access_token` из query (WebSocket) или `Bearer` (negotiate/long polling).
Селектор `Smart` направляет в неё все запросы к `/hubs/*`. Почему не initData в query: она живёт сутки и
является полноценным удостоверением Telegram — в URL (и в логах прокси) ей не место; тикет же через минуту
бесполезен, и `access_token` маскируется в логах (`LogPathMasker`). Ключ подписи — тот же, что у ссылок на
вложения (`Attachments:DownloadSigningKey`), с отдельным префиксом payload (`hub:`) — пересечение с
подписями ссылок невозможно по формату.

Уже установленное соединение живёт после выхода из сессии, пока клиент сам его не закроет (фронт закрывает
при logout). Исключённый из семьи участник остаётся в SignalR-группе до переподключения — см. п. 4, почему это
не утечка.

### 4. В событиях хаба — только идентификаторы

Хаб шлёт `{familyId, messageId, change}` (`created|edited|deleted|reactions`), а клиент перечитывает
сообщение через `GET /api/families/{familyId}/chat/messages/{id}`. Причины:

- карточка ссылки на сущность строится **для конкретного зрителя** (п. 5) — общий payload на группу собрать
  нельзя, не раскрыв заголовок тем, у кого доступа нет;
- любое чтение проходит проверку членства — участник, задержавшийся в группе после исключения, получает
  только непрозрачные GUID.

Цена — лишний GET на каждое событие; для семейного чата это несущественно.

### 5. Ссылки на сущности

Хранится только `(Kind, EntityId)`, **без снимка заголовка**. Разрешение — через `IChatLinkResolver`
(Infrastructure), реализация в Medical: мед-запись (анализ/приём врача), курс приёма, аптечка; проверки
доступа те же, что у самих экранов (`MedicalRecordService.IsVisibleToAsync`, `MedicationCourseAccess`,
членство в семье аптечки). Нет доступа — карточка «Нет доступа» без заголовка. Отправить ссылку можно только
на то, что видит сам автор.

### 6. Вложения

`FileAttachment` с `FileOwnerType.ChatMessage = 5`; шифрование и хранение — как у остальных вложений.
Просмотр — существующими эндпоинтами `/api/attachments/{id}/...`: в `AttachmentService.HasAccessAsync`
добавлена ветка «активный член семьи сообщения». Удаление семьи и аккаунта чистит строки и блобы вложений
чата явно (FK у полиморфного `FileAttachment` нет).

### 7. Уведомления

`NotificationType.FamilyChatMessage`, `NotificationRelatedKind.FamilyChat` (`RelatedEntityId` — id семьи).
После сохранения сообщения ставится Hangfire-задача; получатели — активные члены семьи, кроме автора и тех,
кто прямо сейчас смотрит этот чат (in-memory `ChatPresenceTracker`, сигнал хаба `Viewing`). Дедуп-ключ
`chat:{familyId}:{userId}:{10-минутное окно}` — не больше одного уведомления человеку за 10 минут, колокольчик
не заливается.

Содержимое: в приложении (колокольчик) — «Имя написал(а) в чат семьи «X»», **без текста сообщения**. В
Telegram и Web Push — только обобщённый вид («новое сообщение в чате семьи»), как у всех типов: имена туда не
уходят (политика конфиденциальности). Push получает тег `chat:{familyId}` (новое замещает старое) и переход
на `/families/{id}?tab=chat`.

### 8. Права

Читать и писать — активный член семьи (`FamilyRole.Member`). Править — только автор; удалять — автор или админ
семьи (модерация). Удаление мягкое: текст, ссылки, реакции и вложения стираются, в ленте остаётся «Сообщение
удалено» — чтобы ответы на него не повисали. При удалении аккаунта сообщения пользователя удаляются целиком
(право на забвение), ответы на них теряют цитату.

## Последствия

- Первый realtime-канал в проекте: dev-прокси (`proxy.conf.js`) и Caddy должны проксировать WebSocket,
  `ngsw-config.json` не должен перехватывать `/hubs`.
- Вторая реплика API без бэкплейна сломает доставку событий между репликами — добавлять Redis одновременно.
- Вне v1: личные и групповые чаты, поиск, «печатает…», голосовые, мгновенное выкидывание исключённого
  участника из группы хаба.
