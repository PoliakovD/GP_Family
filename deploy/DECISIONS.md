# Особенности инфраструктуры — почему так, а не иначе

`deploy/README.md` — как выполнить деплой. Этот файл — почему инфраструктура (worktrees, CI/CD,
VPS-стек) устроена именно так, и отдельно — таблица мест, где по ходу реализации всплыли
несостыковки между первоначальным намерением и тем, что реально работает.

## Модель среды: дев по возможностям, прод по защите

| Решение | Почему |
|---|---|
| На VPS `ASPNETCORE_ENVIRONMENT=Production`, не `Development` | `Development` в ASP.NET Core безусловно включает `DeveloperExceptionPage` — любое необработанное исключение отдаёт клиенту полный стектрейс, имена сборок и детали конфигурации запроса. Отключить это флагом из кода нельзя — он встаёт первым в конвейере. На публичном VPS это неприемлемо независимо от того, насколько «дев» контур по духу. |
| Debug-логи и Hangfire/Swagger не завязаны на смену среды | Serilog читает уровень из конфигурации (`Serilog__MinimumLevel__Default=Debug` в `.env`), а не из `ASPNETCORE_ENVIRONMENT` — то, ради чего хотелось остаться в `Development`, достигается без него. |
| `DevToolsOptions` — три независимых флага (`DevAuthEnabled`, `DevEndpointsEnabled`, `AdminUiEnabled`), а не один общий | У каждого своя площадь риска: `DevAuthEnabled` — вход под любым `TelegramId` без пароля (самый опасный), `DevEndpointsEnabled` — служебные эндпоинты без аутентификации по построению (email-превью, ручной запуск джоб), `AdminUiEnabled` — просмотр внутренностей (Hangfire/Swagger), но за собственным BasicAuth. На VPS первые два — `false`, третий — `true`. |
| Guard на утёкший `Encryption:MasterKey` завязан на `DevTools:DevAuthEnabled`, а не на `IsDevelopment()` | Иначе на VPS с `Production` он сработал бы автоматически, но привязка к тому же флагу, что и остальные dev-инструменты, делает поведение однородным и предсказуемым локально и удалённо. |

## Периметр и защита в глубину

| Решение | Почему |
|---|---|
| Caddy, не nginx | Явный выбор пользователя — автоматический TLS от Let's Encrypt без ручной настройки certbot. |
| `UseForwardedHeaders` в начале конвейера | За реверс-прокси `Request.Scheme` всегда `http`, а `RemoteIpAddress` — адрес Caddy. Без этого secure-cookie (JWT, CSRF) выставлялись бы без `Secure`, а партиционирование rate limiter по IP (`Program.cs`) и `RemoteIp` в логах Seq молча сломались бы — ни одной явной ошибки, только тихо неверное поведение. |
| Условный `Strict-Transport-Security` (только при `Request.IsHttps`) | Закрывает находку 6 из `docs/security/module-review-2026-08-02/09-config-deployment-devops.md`, отложенную «до решения по реверс-прокси» — решение принято (Caddy). |
| Hangfire-дашборд и Swagger — за `AdminBasicAuth`/`HangfireBasicAuthFilter`, а не голым `AllowAnonymous` | Защита в глубину: WireGuard — периметр (кто может достучаться), BasicAuth из `.env` — второй, независимый рубеж (кто именно). Один скомпрометированный уровень не открывает доступ полностью. |
| Служебные пути (`/dev/*`, `/hangfire*`, `/swagger*`, `/health/*`) дополнительно блокируются на публичном домене в `Caddyfile` | Защита в глубину поверх `DevTools`-флагов: даже если флаг случайно включат в проде, снаружи с публичного домена эти пути всё равно не достижимы — видны только через админ-блок на WireGuard-адресе. |

## Health checks

| Решение | Почему |
|---|---|
| Три отдельных эндпоинта: `/health/live`, `/health/ready`, `/health/llm` | `/health/live` — только «процесс жив» (для liveness-проб, без обращений к зависимостям). `/health/ready` — Postgres/MinIO/Kafka, тег `ready`, используется `depends_on: service_healthy` и деплой-workflow. `/health/llm` — намеренно отдельно. |
| `/health/llm` возвращает `Degraded`, не `Unhealthy` | LM Studio живёт на ноутбуке пользователя за WireGuard-туннелем — недоступность (сон, выключен) ожидаема и не должна валить общую готовность контура. Использует уже существующую в коде грациозную деградацию (`LmStudioJsonClient` ловит `HttpRequestException`/`TaskCanceledException` и возвращает `Success=false`, а не бросает исключение) — новой логики деградации писать не пришлось. |
| `/health/*` исключены из `UseSerilogRequestLogging` (уровень Debug, не Information) | Иначе Seq заливало бы шумом от healthcheck-поллинга раз в 10-15 секунд. |

## Событийная шина (Kafka) в проде

| Решение | Почему |
|---|---|
| Убран `HOST`-листенер и проброшенный порт `9094` | В дев-стеке он существует только для отладки `kafka-console-consumer.sh` с хоста. На VPS Kafka не должен быть достижим снаружи docker-сети вообще — ни один сервис, кроме Caddy, не публикует портов наружу. |
| `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false` | Топики создаёт сам API при старте (`EnsureTopicsExist`, ADR-0007). Автосоздание в проде означало бы, что опечатка в имени топика тихо создаёт «мусорный» топик вместо явной ошибки при старте. |
| `KAFKA_LOG_RETENTION_HOURS=168` сохранён как в деве | 152-ФЗ: часть событий несёт ПДн (`BirthdayApproachingEvent.PersonName` и т.п.) — ретеншн не должен превышать то, что было у старого `OutboxOptions.ProcessedRetention`. |

## Worktrees

| Решение | Почему |
|---|---|
| `COMPOSE_PROJECT_NAME=familyhub-<slug>` + сдвиг всех `*_PORT` на `slot × 100` в `.env` каждого worktree | `docker compose` по умолчанию берёt имя проекта из имени каталога — это имя префиксует не только контейнеры и сеть, но и **named volumes**. Два worktree с одинаковым `.env` делили бы `postgres-data`/`minio-data` — второй запущенный стек начал бы работать поверх данных первого, без единой явной ошибки. |
| Порт — не UUID/hash, а `slot × 100` | Предсказуемо и читаемо в выводе `worktree.ps1 new` — сразу видно, что slot 1 занимает 5376/5532/9194 и т.д., не нужно ничего расшифровывать. |

## CI/CD

| Решение | Почему |
|---|---|
| Unit-тесты — на каждый push/PR; integration — только на `master` (и по требованию) | Integration-тесты поднимают Testcontainers (Postgres/MinIO/Kafka) — это минуты, не секунды. Блокировать ими быстрый фидбек по фиче на каждый коммит неоправданно; unit-тесты (SQLite in-memory) достаточно быстры для этого. |
| Деплой — только `workflow_dispatch`, без авто-триггера на push в `master` | Явное решение пользователя: контур дев по инструментам (Hangfire, Debug-логи), но ничего не должно уезжать на VPS без явного клика — даже надёжно протестированный коммит. |
| GHCR + SSH pull, а не self-hosted runner на VPS | Сборка (.NET + Angular, ~5-10 минут) не должна отъедать CPU/RAM у самого прод-контура; VPS только скачивает готовый образ. |
| `.env` для VPS рендерится workflow из GitHub Secret `PROD_ENV` и грузится по SSH, а не хранится на сервере вручную | Единственный источник правды — GitHub, ротация секрета не требует захода на сервер; тег образа (`IMAGE_TAG`) решает пайплайн, а не сам секрет — секрет не должен определять, какой билд разворачивается. |
| Продовый `Dockerfile` — отдельный файл, `Dockerfile.dev` не тронут | Дев-стек всё ещё пересобирает `Dockerfile.dev` (быстрее, без Angular — фронт отдельным контейнером с hot-reload через bind-mount). Продовый включает Angular-стадию и собирает единый образ (SPA + API), потому что на VPS одному контейнеру не нужен сосед для фронтенда. |
| В проде — non-root (`USER $APP_UID`) | Дев-образ остаётся под root — не имеет значения для локального docker-compose; на VPS это уже периметр безопасности. |

## Бэкапы

| Решение | Почему |
|---|---|
| Только локально на VPS, без выгрузки за его пределы | Явный выбор пользователя (был предложен и альтернативный вариант — синхронизация на ноутбук через тот же WireGuard-туннель, что и для LM Studio). Принятый риск: полная потеря VPS означает потерю и продовых данных, и их бэкапов — записано как открытый риск, не как недосмотр. |
| Ротация 7 ежедневных + 4 еженедельных дампов Postgres; MinIO — не версии, а актуальное зеркало (`mc mirror --overwrite --remove`) | Вложения неизменяемы после загрузки (`StorageKeyFactory` — опаковые ключи, перезаписи по тому же ключу бизнес-логика не предусматривает) — полная история версий не нужна, важна только точка восстановления «как сейчас». |
| `nullglob` в скрипте ротации вместо `ls`-конвейера напрямую | Обнаружено реальным тестированием: `set -o pipefail` + `ls` на несуществующий литеральный glob (когда файлов ещё меньше `keep`) падает с ненулевым кодом, который `pipefail` протаскивает через весь конвейер и роняет скрипт под `set -e`. Первая версия скрипта именно так и падала на первом же запуске. |

## Таблица: несостыковки

Места, где по ходу реализации обнаружилось расхождение между первоначальным намерением и тем,
что реально работает или уже существует в репозитории.

| Место | В чём несостыковка | Как разрешено / что учесть |
|---|---|---|
| WireGuard-адрес админок | `10.8.0.1` (wg0) — интерфейс **хоста**, а не контейнера. Caddy внутри контейнера физически не может забиндиться на этот адрес напрямую — первоначальная идея «слушать `10.8.0.1:443`» внутри Caddy нереализуема. | Админ-сайты слушают отдельный контейнерный порт `:8443`, который Docker публикует host-IP-scoped маппингом именно на `10.8.0.1` (`10.8.0.1:8443:8443` в compose) — работает на уровне Docker, не требует видимости `wg0` внутри контейнера. Адреса админок теперь с явным `:8443` (`https://seq.gp-family.ru:8443` и т.п.). |
| `Encryption:MasterKey` дефолт | Значение `MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=` навсегда осталось в истории git (было в `docker-compose.yml` до аудита безопасности) и **сегодня всё ещё существует в коде** как `DesignTimeDbContextFactory.DevMasterKey` — не только исторический артефакт. | `Program.cs` блокирует его использование, когда `DevTools:DevAuthEnabled=false`. На VPS в любом случае нужен **новый**, отдельно сгенерированный ключ (`openssl rand -base64 32`) — копировать текущий локальный `.env` нельзя. |
| `.env.example` / `.env` / `prod.env` | Расхождение зафиксировано ещё аудитом безопасности (`docs/security/module-review-2026-08-02/09-config-deployment-devops.md`, находка 2) до начала этой задачи. | Часть ключей досинхронизирована в `.env.example` (`WebPush__*`, `Jwt__Issuer/Audience/...`, `DevTools__*`, `COMPOSE_PROJECT_NAME`, секция «VPS-деплой»). `PROD_ENV` для GitHub Secrets всё равно собирается вручную по инструкции в `deploy/README.md` — не копированием файла целиком, там ещё остаются секреты, требующие ротации. |
| `TECH_DEBT.md` пп. 1–2 | `dotnet ef` игнорирует `ASPNETCORE_ENVIRONMENT` для design-time конфигурации; дев-compose создаёт БД `familyhub`, а `appsettings.Development.json` исторически ссылается на `familyhub_dev`. | Не тронуто — существовавший до этой задачи техдолг, вне её объёма. Учитывать при локальной работе с `dotnet ef` (см. воркэраунд в `TECH_DEBT.md`). |
| Kafka: дев vs прод compose | Дев-стек держит `HOST`-листенер и порт `9094` для отладки с хоста; прод-стек его вообще не имеет. | Конфиги **не взаимозаменяемы** — нельзя скопировать `docker-compose.yml` (дев) поверх `docker-compose.prod.yml` или наоборот, они разошлись по листенерам и режиму автосоздания топиков. |
| Seq: дев vs прод | Дев — `SEQ_NO_AUTH=true` (анонимный доступ); прод — обязательный `SEQ_FIRSTRUN_ADMINPASSWORDHASH`. | Если в `PROD_ENV` случайно попадёт дев-значение (или хеш пуст) — Seq стартует в анонимном режиме прямо за Caddy. Пусть и WG-only, это тихая деградация защиты, а не ошибка старта — стоит явно проверять после первого деплоя (`curl` без креденшлов не должен пускать). |
| Публикация портов: дев vs прод | В деве Postgres/MinIO/Kafka проброшены на хост (`ports:`) для удобства отладки из IDE; в проде — не проброшены вообще, доступ только из docker-сети/через Caddy. | Ещё одна причина, почему compose-файлы не взаимозаменяемы; при отладке прод-инцидента подключаться нужно через `docker compose exec`, не через хостовый порт. |
| CSP `frame-ancestors 'none'` и Telegram Web | Потенциально блокирует Mini App в веб-версии Telegram (`web.telegram.org` открывает Mini App в `<iframe>`) — десктопный/мобильный клиенты используют webview, им всё равно. | Существовало до этой задачи, деплоем не создано и не устранено — открытый риск. Если подтвердится на реальном домене, лечится заменой на `frame-ancestors https://web.telegram.org https://*.telegram.org` в `Program.cs`. |
| Автомиграции на старте | `Database.MigrateAsync()` с retry (`Program.cs`) требует, чтобы пользователь БД приложения владел схемой. | Нормально для одного инстанса на VPS (текущий масштаб); при будущем переходе на несколько реплик потребует внешней блокировки миграций — retry с backoff не заменяет распределённый lock. |
